# 【CAN】核验聊天接口、主人身份与逐条消息来源能力

Type: research
Status: resolved
Parent: [健康管家首发 TO、CAN 与 HOW 决策闭合路线](../map.md)
Blocked by: [【CAN】核验目标 Hermes 基线与受支持的健康扩展面](42-verify-target-hermes-baseline-and-supported-extension-surface.md)

## Question

在已核验的目标 Hermes 扩展面内，聊天接口适配、主人私聊身份授权与逐条消息来源能够提供哪些真实能力和限制：每条物理消息的接口、发送身份、消息标识和接收时间能否在合并或批处理前被健康能力可靠取得并保持；未授权身份和群聊能否失败关闭；回复及运行状态能否保持接口中立并在当前微信接口真实到达？分别给出官方、对应源码与目标运行证据。

## Answer

目标 Hermes v0.20.0 已有接口中立的消息/路由模型，并正式支持 Plugin 注册聊天 Adapter；注册表允许同名 Adapter 覆盖内置实现。当前 Partner 微信配置采用单一私聊白名单、关闭全开放并关闭群聊，源码会在事件创建前拒绝未获准私聊和已收到的群聊事件。这只证明技术准入：白名单值尚未通过真实主人验收确认为产品主人身份，也不等于知情启用、迁移或恢复授权。

当前内置微信路径明确不能满足逐条物理消息来源要求。它除按消息标识去重外，还在 300 秒内按“发送身份 + 相同正文”去重，可能丢掉标识不同的第二条真实消息；快速文本又按当前默认的 3 秒或 5 秒窗口合并，只保留第一条事件的消息标识、本机处理时间和原始消息。`pre_gateway_dispatch` 只能看到合并后的事件，不能补回已丢失的逐条来源。

回复路由可以交回来源聊天 Adapter，但微信所谓发送成功只表示 iLink 接口未报告错误，返回标识是 Hermes 自生成的客户端标识，不是主人微信展示、收取或已读证明。现场最近可连起的入站到发送链停留在 2026-08-11；本次未发测试消息，因此 2026-08-16 当前真实到达仍未证明。健康插件运行状态也尚不存在，由后续调度、恢复与状态 CAN 票继续核验。

由于官方扩展面允许 Plugin Adapter 覆盖内置 Adapter，当前证据仍存在在 Hermes 架构内解决逐条来源的空间，暂不创建 TO-CAN 差距决策，也不降低产品目标。后续 HOW 不得把内置 Adapter 之后的 Hook 当作合并前逐条入口。完整源码、现场配置、日志边界与未证明项见 [聊天接口、主人身份与逐条消息来源能力核验](../evidence/03-channel-owner-provenance-capabilities-20260816.md)。
