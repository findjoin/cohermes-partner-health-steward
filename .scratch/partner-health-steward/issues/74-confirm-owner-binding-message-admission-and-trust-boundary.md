# 【TO】确认首次主人绑定、消息准入与首发信任边界

Type: grilling
Status: resolved
Parent: [健康管家首发 TO、CAN 与 HOW 决策闭合路线](../map.md)
Blocked by: [【TO】确认首发健康管家的基础产品能力与不可妥协边界](53-confirm-foundational-product-capabilities-and-boundaries.md); [【TO】确定主人授权聊天身份变化后的健康画像连续性与恢复边界](38-define-owner-identity-continuity-boundary.md); [【TO】确定旧状态恢复下的身份失效与健康管家启用边界](67-decide-owner-recovery-anti-rollback-launch-promise.md)

## Question

首发健康管家在产品层面如何把一个预先指定的私聊候选身份变成唯一画像主人；知情启用和恢复准备完成前、来自未授权私聊、群聊、身份或私聊属性无法确认的消息分别给出什么主人可见结果并保存什么；健康、混合和无法确认是否健康的消息能否回退普通聊天；哪些风险由当前可信应用边界承担，哪些主动对抗明确不承诺？

本票必须打破“未授权消息只能拒绝”与“候选身份必须先完成知情启用”的循环：明确一条尚不授予读取、写入或健康处理权利，但足以让预先指定候选身份完成启用与恢复准备的主人可见路径；同时确认产品只证明候选聊天身份的当前控制权，还是还承诺验证现实世界中的自然人身份。不能用“本人完成绑定”循环定义本人，也不能让首次消息、技术白名单或管理员声明自动取得健康权利。

首发信任边界必须覆盖恶意最高权限主体能够替换或篡改 Plugin、进程、运行时明文和解密材料的完整影响，而不只写“替换 Plugin”；被选定域外信任锚的最高控制主体能够破坏该信任边界时同样不在首发主动对抗承诺内。该边界失去可信时，产品必须停止可信健康处理声明。具体信任锚是什么、由什么账号或服务控制，留给 CAN/HOW。

本票必须把此前散落在 HOW Ticket、ADR 和 `CONTEXT.md` 中的主人可见准入、失败关闭与信任边界重新确认为技术无关的 TO。它不得选择 Adapter 覆盖、Hook、消息字段、数据库、身份凭据、云服务或其他实现方式，也不得篡改历史 HOW Answer 来伪造产品确认。

## Comments

### 2026-08-18 — Authority normalization input

当前 [【HOW】选择健康管家在 Hermes 中的单一执行与权威路线](47-choose-hermes-health-execution-and-authority-route.md) 已包含“健康、混合或无法确定的消息不回退普通聊天”的产品失败结果；[【HOW】选择微信接入、主人授权与逐次来源路线](48-choose-channel-identity-and-provenance-route.md) 已包含首次候选身份接受、未授权私聊通用拒绝、群聊静默、正文不保存、重投歧义和处理结果无法确认等产品语义。这些内容是本票的历史输入，尚不能因为位于已解决 HOW 中就冒充完整 TO 已闭合。

主人已确认首发信任边界：产品应防止未授权身份、重放、模型错误和磁盘泄露等既定风险，但不承诺抵抗恶意 guest root 替换 Plugin，或外部云账号管理员摧毁整个信任边界。该边界必须在最终 TO 中明确披露；若以后需要扩大主动对抗范围，应建立新的 TO，而不是在 HOW 中静默加入。

本票仍需在一次 HITL 会话中汇总全部准入与失败结果，确认其与当前单一活动主人身份、永久删除、身份恢复和普通聊天隔离边界一致后才能解决。解决本票前还必须明确标记 ADR 0018、0019 中与当前首跳模型服务路线和单一活动身份冲突的旧条款已被取代或收窄，不能让已确认 ADR 与现行 TO 并存为两个答案。

### 2026-08-20 — HITL 场景轮 1

主人决定产品无需证明现实世界中的自然人身份，也无需以“预先指定候选身份”证明谁是主人；每个 Hermes 只由一个人使用，和该 Hermes 聊天的默认使用者就是画像主人，这项单人专用前提由上线者保证。主人以“同理”回应启用前候选路径及其他私聊、群聊和来源不明消息的场景；由于该表述可能同时指“取消实名核验”或“取消全部消息准入”，且会实质改写既有单一活动身份、迁移和恢复合同，后续必须继续用具体场景消歧，不能由 AI 猜测。

主人确认：正式启用后，明确非健康消息可走普通聊天；健康、混合或无法排除健康风险的消息只走健康管家并且不回退普通聊天；处理前明确失败与处理结果无法确认必须给出不同真实结果。主人也确认：无法区分接口重投与主人再次发送时，不静默丢弃、不自动产生第二次健康效果；仅在歧义影响判断或下一步时询问主人，危险处理不等待消歧，结果未知时不自动重试。

### 2026-08-20 — HITL 场景轮 2

主人确认单人专用 Hermes 的默认使用者仍必须先完成健康管家初始化，只有初始化完成后才启用健康处理；单人部署前提不能替代初始化。初始化是已确认的产品能力与入口，是否具体映射为 Hermes Skill、Tool 或其他机制仍由后继 CAN/HOW 决定。

对于其他私聊、群聊、来源不明消息以及换号/丢号，主人要求先根据微信接口和 Hermes 的真实特性判断，并指出 Hermes 可能已有只接受特定消息的白名单；如属实，只需正确配置白名单。该问题属于必须由 AI 核验的事实前提，不能继续让主人凭记忆选择；Q7、Q8 暂不视为已闭合，待核验白名单的覆盖范围、失败表现以及它能否安全承接身份变化后再以场景返回。

### 2026-08-20 — 白名单事实核验结果

已解决的 CAN 与现场证据确认：目标 Hermes v0.20.0 确有微信私聊 allowlist，当前 Partner 配置为单值私聊允许清单、全开放关闭、群聊关闭；未获准私聊和已收到的群聊会在创建后续聊天事件前停止。因此，首发可以依靠正确配置的单人私聊白名单建立技术消息入口，健康管家无需再做现实自然人核验；白名单无法证明时不得把任意来信者视为主人。

白名单只证明某个技术发送身份可以进入 Hermes，不证明主人已知情启用，也不提供旧端发起/新端接受、主人专属恢复权、画像与控制状态连续性或防旧状态回滚。修改白名单可以是首次交付配置，或迁移/恢复成功后的入口切换动作，但按当前事实不能单独证明新号有权接管既有健康画像。Q7 的事实前提与产品路线已闭合；Q8 仍需主人决定上线者的保证只用于首次交付，还是允许上线者以后成为第三方恢复权威。

### 2026-08-20 — 主人将身份恢复问题改为健康管家可迁移性

主人决定不再把换号后的身份迁移、身份恢复或永久锁定作为本票需要解决的问题。健康管家被理解为由权威产品文档、健康画像与证据关系、任务记录及配套 Skill 共同承载的持续框架；首发只需保证健康管家可以迁移到另一台单人专用 Hermes，并由目标 Hermes 的唯一白名单入口继续使用。

这项决定实质改变了 Ticket 38 与 Ticket 67 的既有主人专属迁移、一次性恢复权、防旧状态回滚和不可恢复锁定合同，不能继续把两套目标并列为现行答案。后续需要用一个具体迁移场景确认“只迁移通用框架”还是“连同主人画像、个人证据、任务与控制状态一起连续迁移”，以及迁移后旧 Hermes 是否必须失去健康资料访问；在该产品结果明确前不进入 CAN/HOW。

### 2026-08-20 — 主人将可迁移性归回文档化框架与 HOW

主人进一步澄清：LLM 本身无持久记忆，健康管家依靠外部权威文档、健康画像、证据库、任务记录与 Skill 运行；以后需要迁移时搬迁这些文档和 Skill 即可，不需要在 TO 中新增账号恢复或独立的健康管家迁移产品流程。由此，健康管家的现行产品边界是不把不可替代状态藏在 LLM 会话记忆中；画像、个人证据、任务与控制状态本来就是受管文档关系的一部分，而不是另一个待选择的迁移对象。具体文件集合、复制、校验、源/目标切换和部署步骤属于后继 CAN/HOW。

本决定明确取代 Ticket 38 的聊天身份迁移、一次性恢复权、第三方不得代办与不可恢复锁定目标，也取代 Ticket 67 因身份恢复防回滚而阻止初始化和上线的 No-Go；永久删除不得恢复、已撤回批准不得复活、结果未知不得盲目重做等由各自独立产品合同继续约束。历史 Answer 保留为历史，由本票及 Map 标明取代范围，不回写旧票伪造历史。

### 2026-08-20 — HITL 初始化前运行边界

主人明确决定：健康管家在初始化完成前不启动。初始化入口属于启动健康管家的引导能力，不表示完整健康管家已经运行；初始化成功前，健康管家不检查消息是否健康、不读取或写入健康画像、不形成健康证据、任务、诊断或危险处理，也不保存健康管家自己的最小接收事实。此时只有基础 Hermes 按其普通聊天合同运行。初始化成功后，健康、混合或无法排除健康风险的消息才进入已确认的健康管家专属路径，不得回退普通聊天。

## Answer

首发采用“单人专用 Hermes”作为主人前提：每台 Hermes 只交给一个人使用，这项事实由上线者保证；产品不核验现实世界中的自然人身份，也不再建立“预先指定候选身份—本人绑定—身份恢复”的主人证明流程。和该 Hermes 的唯一获准私聊入口交互的人，在产品语义上就是画像主人。如果实际使用者已经变化、获准账号或设备被他人控制而上线者没有发现，产品无法识别屏幕后换了人。

### 初始化前后

- 健康管家提供独立、可发现的初始化入口。初始化说明健康资料范围、每日复盘、健康任务、主动支持、数据接收方和主人权利，取得主人明确同意，确定主人时区与基础行为偏好，并创建初始健康画像；不再要求建立身份恢复权利。
- 初始化完成前，完整健康管家不启动：不判断消息是否健康，不读取或写入健康画像，不形成健康证据、健康任务、诊断性判断或危险处理，也不保存健康管家自己的消息接收事实。未完成的初始化不能因主人继续聊天或提到健康而自动完成。
- 初始化前的其他消息由基础 Hermes 按普通聊天合同处理。即使主人此时谈到胸痛、自伤或用药，健康管家的隔离、证据、任务、危险升级和记录承诺也尚未生效；基础 Hermes 是否回复或保存普通会话不属于健康管家合同。初始化后不得把此前普通聊天内容倒填为画像、证据或任务，主人如需健康管家处理，应重新提供相关信息。
- 初始化成功后才保存知情启用结果、启动健康管家并开始履行本 Map 中已经确认的健康产品合同。

### 唯一消息入口

- 当前微信首发依靠已经核验存在的单值私聊白名单，并关闭全开放和群聊入口。健康管家信任这一个技术入口，不对入口背后的自然人进行第二次身份核验；白名单不能代替初始化或知情同意。
- 白名单之外的私聊、群聊以及未能作为唯一获准私聊入口交付的消息不进入健康管家。因此健康管家不读取、不回复、不保存其正文、媒体或健康内容，也不据此建立画像、证据或任务；通信平台或基础 Hermes 自身可能产生的运行记录不属于健康管家数据。
- 所有可到达健康能力的人类入口必须属于同一位单人使用者，或不能访问健康能力。若无法证明唯一白名单、关闭全开放、关闭群聊以及其他入口不会绕过该边界，健康管家不得视为可用，也不得声称正在可信处理健康资料。
- 该路线删除了原问题中的绑定循环：唯一入口决定谁能到达这台单人 Hermes，知情初始化独立决定健康管家何时开始运行；产品不再先寻找一个尚未授权的候选主人。

### 初始化后的逐条处理结果

- 唯一入口中的消息只有在明确无关健康时才进入普通聊天。涉及健康、同时包含健康与普通请求，或者无法排除健康风险的消息，整条只由健康管家处理并只产生一个受控结果，不得并行交给普通聊天，也不得在健康能力不可用时回退普通聊天。
- 若能够证明处理在产生任何健康记录、任务、判断、回复或外部效果前已经失败，主人看到的结果必须说明当前无法安全处理且没有形成健康记录，不得继续给出健康建议。
- 若处理中断后无法证明画像、证据、任务、回复或外部动作是否已经发生，主人看到的是“处理结果无法确认”。产品既不能声称成功，也不能声称没有记录，并且不能自动重做可能产生重复效果的动作；是否承担重试风险由主人决定。
- 初始化前由基础 Hermes 处理普通聊天，与初始化后健康消息不得回退普通聊天是两个阶段，不构成例外或冲突。

### 重复投递与重复效果

- 两次实际观察到的消息即使正文相同，也保留为两次来源事实；消息标识相同、不同或发送时间接近，都不能单独证明它们是接口重投还是主人有意再次发送。
- 无法消除歧义时，不静默丢弃第二次来源，也不自动产生第二次画像更新、任务变化、诊断结果、回复或其他健康效果。只有该歧义会改变健康判断或下一步时才向主人确认一次；未确认前保持未决，明确危险处理不得等待消歧。
- 已经确认完成的效果不重做，能够确认尚未发生的效果才可继续；结果未知时不自动重试。

### 权威状态与可迁移性

- LLM 会话记忆不是健康管家的权威状态。健康管家依靠受管的产品文档、健康画像、证据库、健康任务记录、批准与控制状态以及配套 Skill 持续运行；普通聊天历史与通用 Memory 不得成为第二份健康画像或隐藏权威状态。
- 健康管家的可迁移性来自这些权威资料与 Skill 可以随产品搬迁，而不是来自账号恢复或 LLM 记住过去。具体文件和状态清单、复制与校验、源端与目标端切换以及部署步骤属于后继 CAN/HOW。
- 首发不新增聊天账号迁移、一次性恢复权、第三方恢复、不可恢复身份锁定或独立迁移向导等产品流程。目标 Hermes 的白名单配置与资料搬迁同样是后继能力和部署问题，不在 TO 中另造身份判断。

### 首发信任边界

- 在可信前提成立时，产品必须防止准入外消息进入健康处理，防止重投直接产生未经判断的重复健康效果，约束模型输出不能越过证据与安全边界，并保护持久健康资料不因普通聊天、日志或磁盘明文而泄露。
- 首发不承诺抵抗已经恶意控制 Hermes 所在环境最高权限的主体；这类主体能够替换或篡改健康 Plugin、进程、权威文档和状态，读取或修改运行时明文、解密材料及健康资料。被选作边界外依赖的云服务、账号或其他信任锚，其最高控制主体若能够摧毁整个信任边界，同样不属于首发主动对抗范围。
- 唯一获准账号或设备实际被他人控制、上线者把一台 Hermes 交给多人使用、白名单配置错误，均超出产品辨认现实身份的能力。产品承诺在已声明的单人使用和可信入口前提内正确运行，不冒充能够识别屏幕后的人。
- 一旦知道或无法证明上述可信前提仍然成立，健康管家必须停止可信健康处理并如实显示不可用或无法确认，不能继续显示“活跃”或声称已经安全完成处理。

### 对既有决定的取代与保留

本答案是当前主人前提、初始化准入、消息分流和首发信任边界的现行 TO。历史票据与 ADR 保留为当时的决定记录，但以下冲突内容不再是当前产品要求：

- [确认首发健康管家的基础产品能力与不可妥协边界](53-confirm-foundational-product-capabilities-and-boundaries.md)中，“只有另行完成身份授权的私聊身份才能成为主人”收窄为“单人专用 Hermes 的唯一白名单私聊入口默认代表主人”；初始化中的身份授权和恢复准备改为唯一入口条件、知情同意、时区和基础行为偏好。该票确定的单一健康画像、健康能力、证据、安全、主人权利、每日复盘、主动支持和真实微信验收等其他合同继续有效。
- [确定主人授权聊天身份变化后的健康画像连续性与恢复边界](38-define-owner-identity-continuity-boundary.md)中的旧身份发起与新身份接受、一次性主人恢复权、第三方不得代办恢复、身份恢复通知、异常尝试记录及全部身份与恢复权利丢失后的不可恢复锁定，全部由本答案取代，不再是首发目标。单一健康画像和既有证据来源不得被改写等由其他合同独立支持的原则继续有效。
- [确定旧状态恢复下的身份失效与健康管家启用边界](67-decide-owner-recovery-anti-rollback-launch-promise.md)中，围绕旧身份、恢复权和不可恢复锁定建立的防回滚 No-Go 不再阻止初始化、产品验收或上线；“身份恢复状态无法确认即停止全部健康处理”改为“唯一入口或整个可信边界无法证明时停止健康处理”。主人永久删除后不得恢复仍然有效。
- [确定健康任务的自动生成、派发与生命周期合同](73-define-health-task-generation-dispatch-and-lifecycle-contract.md)中，以聊天身份迁移或恢复延续任务和批准的专门流程不再适用。任务、批准与控制状态继续作为受管权威资料存在；任何未发送动作仍须按当前任务目标、接收方、允许资料、批准范围和外部效果重新判断。已经撤回的批准不得由旧资料、旧 Plugin 状态或旧备份复活，结果未知不得盲目重做，其余任务合同继续有效。
- ADR 0010 中的恢复码与身份迁移路线退出首发目标，“当前模型供应商”按现行合同收窄为主人同意的首跳模型服务路线及其正常内部路由与故障切换；明确知情启用和主人数据控制继续有效。
- ADR 0018 关于单一 Partner Hermes、不设第二健康 Agent、Hermes 停止时健康能力停止、恢复后不补发积压的决定继续有效；其中接收方表述由 Ticket 58 收窄为首跳模型服务路线，信任边界由本答案扩展到 Plugin、进程、运行时明文、解密材料和边界外信任锚的最高控制主体。
- ADR 0019 的“每条主人消息均检查健康内容”只在初始化成功后成立；其多个绑定私聊渠道、来源不完整时普通聊天仍可继续及固定技术字段等旧条款不再是当前产品要求。首发只有一个白名单私聊入口，初始化后的健康、混合或无法确定消息不得回退普通聊天；健康资料独立于普通聊天历史并保留真实来源的原则继续有效。
- 历史 HOW 中的候选身份绑定、本人接受和恢复准备不得再冒充当前产品要求；其中已经核验的微信入口、逐条来源、重投歧义和结果无法确认事实仍可作为后继 CAN/HOW 的历史输入。不得回写历史 Answer 伪造当时已经采用本答案。

不受上述取代影响的不变量包括：健康管家启动前必须取得明确知情同意；只维护一份健康画像和一个逻辑证据库；健康管家启动后的受管健康资料不进入普通聊天历史或通用 Memory；主人保有查看、纠正、导出、停止新增记录、暂停主动支持和永久删除权；永久删除后的内容不得恢复；已撤回批准不得复活；可能已产生外部效果但结果未知时不得自动重试；故障或恢复后依据当前状态重新判断而不倾倒积压；明确危险不得等待普通任务或重复消息消歧。

本答案只确定主人可理解的产品结果和信任假设，不选择 Adapter、Hook、消息字段、数据库、身份凭据、文件格式、云服务、迁移命令或其他实现方式。
