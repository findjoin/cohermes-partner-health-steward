# 16 — 让一条已同意的健康微信消息可信入档

**What to build:** 让预配置画像主人在微信中明确启用健康记录后，其第一条可信健康陈述能够经过真实格式入站事件、独立收据签发、fresh 健康判别和 sidecar 校验形成可追溯画像更新，并只在实际写入成功后显示健康管家尾标。

**Blocked by:** None — can start immediately

**Status:** resolved

- [x] 未明确同意前不运行健康判别、不绑定主人、不创建健康档案；服务器管理员、查看者和关系身份均不能代替主人同意。
- [x] 只有预配置主人 sender ID 的第一条已认证消息能在同意后完成绑定，其他 sender 的消息失败关闭且不泄露档案是否存在。
- [x] 入站链路保留认证后、文本合批前的准确 sender ID、message ID、UTC 时间、渠道/profile 和必要原文；多消息合批不能借用第一条消息的身份或时间。
- [x] 独立窄权限签发端把消息身份和动作签入收据；Gateway 主进程可以请求签发，模型工具子进程不能读取私钥，sidecar 只持独立验证公钥。
- [x] 健康候选使用单独固定的健康模型配置和 fresh 调用生成，普通聊天会话历史不作为判别输入或个人健康事实。
- [x] 一条主人直接健康陈述经 sidecar 验证后形成证据、不可变画像版本和不超过 300 字的当前画像；伪造、重放或字段不一致的收据不产生部分写入。
- [x] 只有 sidecar 确认画像或证据实际改变后才显示健康管家尾标；模型声称成功、失败写入和无变化写入均不能显示成功尾标。
- [x] 主验收从真实格式微信事件经过生产 adapter/plugin、签发端和 Unix socket，到微信可见尾标、授权查询结果和无内容审计闭合。

## Answer

新增 partner 专用微信 adapter，在 Hermes 完成微信准入后、原生文本合批前逐条建立受信封套；同意状态与画像分开保存，明确启用不会提前创建档案，第一条经核验的直接健康陈述才在一次 sidecar 原子变更中绑定预配置主人并生成证据、不可变版本和当前画像。错误 sender、未同意、伪造、字段不一致和重放请求均失败关闭。

新增独立 Ed25519 收据签发服务。私钥只存在于该窄服务，Unix socket 同时核对 Gateway 主进程 PID 与 UID；sidecar 只持公钥。健康判别使用独立配置文件固定供应商、HTTPS 端点、模型、隐私模式和 partner 凭据域，沿用 Hermes 插件信任策略，但绕过会自动切换供应商的通用回退链；端点或模型漂移会在发送健康正文前失败关闭。普通聊天历史不进入判别请求。

微信成功尾标由生产 adapter 根据 sidecar 的 `changed=true` 附加，模型不能自行声称写入。主 seam 测试以真实格式微信原包穿过生产 adapter、签发 socket、sidecar Unix socket、授权查看和无内容审计；Linux 还额外验证同 UID 工具子进程不能借用 Gateway 的签发权限。

验证证据：Ticket 16 定向测试运行 25 项，其中 23 项通过、2 项因当前 Windows Python 缺少 Linux AF_UNIX/`SO_PEERCRED` 能力跳过；Hermes 插件定向运行 10 项，其中 9 项通过、1 项环境依赖跳过；sidecar 定向运行 49 项，其中 40 项通过、9 项平台能力跳过；全量运行 368 项，其中 348 项通过、20 项平台或环境能力跳过。新增回归证明删除后旧入站收据不能重建画像、审计失败会回滚画像写入、突发消息共享从事件入队起算的 15 秒总入站预算且仍按微信原始顺序进入合批；超时会立即放行普通聊天，Gateway 关停会通知工作线程停止。签名收据另外绑定本次尝试时间，sidecar 在状态与审计共同提交后再次校验 15 秒尝试窗口，跨线会同时回滚二者；原封套仍能在 10 分钟内凭新的重试尝试接纳，不会阻塞 Ticket 18 的一次重试路线。生产 signer 和 sidecar 协议均把尝试时间列为 consented-admit 必填字段，旧 stage 接口保持兼容。`compileall` 与 `git diff --check` 通过。代码实现已完成，但真实 DMIT 的 Linux 凭据边界、微信联网与部署配置仍属于恢复 Ticket 14/15 后的生产验收，本结果不表示已经部署或上线。
