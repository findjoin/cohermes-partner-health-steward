## Question

主人已经确认新增一个危险升级的产品方向：健康管家确认危险升级时，由不可绕过的健康安全边界选择并直接给主人呈现预先约束、固定、非诊断、非个性化且无用药调整内容的紧急行动提示，不由 LLM 临场生成；同时可以并行向主人预先批准的支持联系人尝试发送最小警报。联系人警报只作附加支持，不能替代主人提示。该联系人不是第二画像主人，不因收到警报而获得查看、纠正、导出或控制健康画像、证据、任务和诊断的权利。

本票只用具体危险场景闭合这一新增产品能力的主人可见结果、数据接收方、授权、记录、失败和删除边界，不选择“另一 Hermes 用户”、微信、电话、具体账号、接口、消息 schema、数据库、重试算法或其他实现机制。至少逐项确认：

1. **触发边界**：只有当前可信最小证据满足经审核且适用的“危险升级”条件时，还是“危险未明”或“安全能力不可用”也可以向联系人外发；没有命中危险规则不得冒充已经安全，资料不足或安全能力失效也不得冒充已确认危险。
2. **支持联系人身份与知情**：谁可以成为联系人，主人怎样预先指定、查看、更换、暂停或撤回，联系人是否必须明确同意接收，以及接收身份或路线变化时旧批准怎样失效；联系人不得自动成为健康管家入口或画像共同控制者。
3. **最小警报内容**：联系人至少和至多看到哪些事实，是否只说明“请立即联系主人并协助其寻求紧急帮助”、事件时间和必要行动，什么情况下可以包含位置、症状类别或其他健康内容；不得发送诊断方向、整条主人消息、完整画像或证据库。
4. **主人可见结果**：给主人固定紧急行动提示与联系人警报怎样并行呈现；结果形成、发送尝试、接口接受、联系人到达／已读和联系人实际采取行动保持为不同事实，任一层不得冒充下一层。
5. **授权与控制**：联系人、健康目的、允许资料、允许外部效果和有效边界怎样形成可撤回批准；每次尚未发送的警报怎样重新核验当前联系人、允许资料、触发范围和批准仍然有效，无法证明时不得外发；暂停主动支持、停止新增记录、联系人警报暂停、任务取消和永久删除分别怎样作用，不能彼此替代。联系人警报属于危险升级的受控外部效果，不建立为普通健康任务；普通任务取消不能代替联系人警报批准的暂停或撤回。
6. **发送失败或无法确认**：联系人离线、身份无法确认、发送被拒绝、接口接受但到达未知、进程崩溃或结果未知时，给主人显示什么；是否允许预先批准的有限重试或备用联系人，何时必须冻结自动重试，且联系人路线失败不得取消或降低给主人固定紧急行动提示。
7. **误报、纠正和最小留存**：后来证据表明原警报可能错误时怎样保留真实历史和必要纠正，不能冒充已经撤回第三方看到的内容；正常记录、停止新增记录和永久删除下分别允许保留哪些最小危险事件、联系人批准引用及发送／到达事实，不得借警报保存完整聊天或形成第二证据库。

至少用以下对照场景闭合：主人独处且联系人在线；主人从未配置联系人或当前没有有效批准；联系人离线或消息到达未知；主人已停止新增记录；主人撤回联系人批准后再次出现危险；联系人账号或技术地址已经变化；警报发送后发现触发依据被纠正；主人永久删除后旧任务或旧备份恢复；永久删除前联系人已经收到站外副本；危险未明与安全能力不可用但尚未确认危险。每个场景都必须说明主人收到什么、联系人收到什么、记录什么、不记录什么、能证明到哪一层以及什么不得发生；本地永久删除不得冒充已经撤回联系人此前收到的站外内容。

完成条件：主人确认联系人角色、触发、最小内容、授权／撤回、控制优先级、失败／未知、误报纠正、留存与永久删除边界；逐项明确修订或保留[危险升级、危险未明与安全能力不可用合同](64-define-diagnostic-scope-and-safe-unavailable-result.md)、[诊断证据接收方与留存合同](65-define-diagnostic-evidence-recipients-and-retention-boundary.md)、[健康任务派发与外部效果合同](73-define-health-task-generation-dispatch-and-lifecycle-contract.md)、[完整首发产品合同](75-close-first-release-health-steward-product-contract.md)、[永久删除合同](39-define-permanent-deletion-backup-promise.md)、[模型首跳接收方合同](58-decide-health-model-recipient-lock-gap-boundary.md)和[唯一画像主人及信任边界](74-confirm-owner-binding-message-admission-and-trust-boundary.md)中的哪些既有结果；`CONTEXT.md` 同步技术无关术语；本票形成唯一 `## Answer`。由于该结果实质新增第三方健康数据接收方与自动外部效果，本票解决后必须按 Map 规则更新完整最新 TO 到 CAN 的追溯链，新增联系人接收、批准、发送／未知与安全强制能力节点，并完整重审受影响的 CAN/HOW；未受影响且证据仍当前的 CAN 事实可以明确继承，受影响旧结论只作历史输入，不能仅补一项发送接口而跳过安全、隐私和失败链。

## Answer

危险支持联系人是健康管家危险升级结果中的**单向、附加支持接收者**，不是第二画像主人、健康管家入口、普通健康任务承担者或健康资料控制者。首发采用以下完整产品合同；它决定主人和联系人应得到什么、系统可以保留什么，不决定 Hermes 用户、微信、电话、账号、接口、数据结构、数据库或重试算法。

### 1. 触发、主人提示与联系人资格

- 只有当前可信最小证据满足已获准、经审核且适用的危险升级条件时，才允许形成联系人警报。危险未明继续只适用既有最小安全澄清／及时人工评估结果，安全能力不可用继续只适用既有最低求助提示；二者均不向联系人外发，安全规则没有命中也不等于已经证明安全。
- 危险升级成立后立即停止本次诊断性输出。健康安全边界始终直接给主人呈现预先约束、固定、确定性、非诊断且无个体化治疗或调药内容的紧急行动提示，不由 LLM 临场生成。联系人警报与该提示并行，任何联系人配置、发送失败或未知都不能取消、降低或延迟主人提示。
- 首发发布时预置一个具体联系人及联系方法，不配置备用联系人。上线者在线下确认该联系人已经知情并愿意接收，这是发布前提；产品不要求联系人通过 Hermes 再确认，也不记录或冒充能够证明线下协商。
- 初始化必须向主人明确显示联系人、联系方法和自动危险警报作用。主人启用整个健康管家时一次性批准该内置能力；发布者只写入配置但主人尚未启用，不构成授权，初始化成功前不得形成或发送联系人警报。启用后主人可以查看、暂停、撤回或更换；联系人或路线变化后必须重新满足线下知情前提并取得主人对新接收身份与路线的批准，旧批准不得沿用。
- 没有当前有效联系人时，健康管家及主人固定提示仍可用，只把联系人警报能力显示为不可用；系统不猜测替代接收者、不复用旧路线，也不自动改向备用联系人。

### 2. 最小警报、主人可见结果与外部效果层级

- 默认警报只表达“这是主人预先授权的紧急警报，请立即联系主人并协助其寻求紧急帮助”，并包含联系人可识别的主人称呼和事件时间。它不包含诊断方向、主人原消息、症状类别、位置、画像或证据正文；以后增加任何这些资料都必须重新形成产品决定与批准。
- 主人在固定紧急行动提示之外看到具体联系人和当前能够证明的最高交付层级：未尝试、已尝试、接口接受、已送达、已读、失败或无法确认。结果形成、发送尝试、接口接受、送达、已读和联系人实际行动是不同事实；接口接受不等于联系人看到，已读也不等于联系人已经联系主人或采取行动。
- 每个尚未发送的警报都必须重新核验危险升级仍成立、当前联系人／路线仍有效、允许资料仍是本票最小集合且主人批准仍有效；任何一项无法证明即不外发。
- 联系人警报及其必要纠正都是危险升级的受控外部效果，不建立为普通健康任务。暂停主动支持、停止新增记录、普通任务取消或普通通知选择都不能代替专门的联系人警报暂停／撤回，也不能改写已经发生或无法确认的外部效果。

### 3. 失败、重试、纠正与控制

- 只有能证明警报请求尚未发出或已明确被拒绝、没有产生外部效果时，才允许在重新核验危险升级、联系人及批准仍有效后，按预先批准的有限策略自动重试。请求可能已发、接口已接受但送达未知、处理中断后外部效果未知、已经送达或已读时，均冻结自动重发。具体次数和间隔留给 CAN/HOW。
- 首发只有一个联系人。警报失败或未知时如实给主人显示，不自动转发给其他人。
- 原警报已经或可能已经离开系统后，证据纠正使危险升级条件不再成立时，向**同一联系人**形成一次最小必要纠正，只说明此前警报依据已经变化、当前不再维持原危险升级状态。原警报可证明未发出时不发送纠正；纠正不能冒充撤回联系人已经看到的内容，其发送未知时也不盲目重发。
- 暂停未来联系人警报不阻断上述必要纠正；联系人已经撤回、原接收身份／路线不再能证明有效或已经永久删除时，不再发送。主人必须看到原警报、纠正以及无法完成纠正各自能证明的结果。
- 停止新增记录期间，系统仍可为当次处理临时判断危险、给主人固定提示并发送已批准的最小联系人警报；不得新增长期个人事实、危险升级事件、危险未明状态、诊断或其他健康正文。只有专门暂停／撤回联系人警报，或永久删除，才阻止尚未发送的警报。

### 4. 最小留存与永久删除

- 正常记录时，只在既有最小危险事件上链接而不复制：触发它的最小可信证据与安全依据、主人固定提示及交付状态、当时联系人／联系方法与批准版本、固定警报／纠正语义版本、事件时间，以及警报和纠正各自可证明的发送／到达层级。纠正追加真实历史关系并把原状态标成不再维持，不覆盖或删除原警报历史。
- 不保存警报／纠正全文、完整聊天、整条健康消息、模型提示或草稿，不复制症状、画像、证据正文或诊断来建立第二证据库。
- 停止新增记录时，不新增上述健康事件或含健康正文的纠正历史；只保留防重复、当前批准／接收方引用、警报与必要纠正的尝试、送达或未知所需的无健康正文最小操作事实。停止前已有历史不删除，停止期间临时健康材料在处理闭合后清除，恢复记录后不倒填。
- 永久删除立即阻止尚未发送的警报与纠正，并删除全部本地危险事件、联系人配置与批准、警报／纠正、交付及未知事实；不等待站外结果，不继续追踪，也不保留本地审计例外。旧任务、备份或旧实例不得复活联系人、批准或发送能力。联系人已经或可能收到的站外副本无法由本地删除撤回，只能在删除前如实说明这一边界。

### 5. 代表性场景结果

| 场景 | 主人结果 | 联系人结果与本地边界 |
|---|---|---|
| 已确认危险，联系人当前有效 | 立即看到固定紧急行动提示、联系人和真实交付层级 | 只收到最小警报；“在线”本身不证明送达，正常记录仅留引用与分层交付事实 |
| 从未配置、已撤回或路线变化后未重新批准 | 固定提示照常，联系人能力显示不可用 | 不发送、不猜替代者、不沿用旧路线 |
| 联系人离线、接口接受但到达未知或处理中断 | 固定提示照常，并显示失败或无法确认 | 只有证明未发／明确拒绝才有限重试；可能已发即冻结，不换人 |
| 已停止新增记录 | 固定提示和已批准最小警报照常 | 不新增健康事实，只留无正文防重复与交付／未知事实，不倒填 |
| 原警报可能已达，后续依据被纠正 | 主人看到原警报和纠正各自状态 | 同一有效联系人收到一次最小纠正；不能冒充撤回，纠正未知不重发 |
| 危险未明或安全能力不可用 | 只得到各自既有主人安全结果 | 不向联系人外发，不把未知或系统故障冒充危险升级 |
| 永久删除前联系人已收到，随后删除或旧备份恢复 | 删除立即生效，不等待站外结果 | 本地全部清除且旧实例不能复活；站外已收副本不能冒充已撤回 |

### 6. 对既有产品合同与后继阶段的影响

- [Ticket 64](64-define-diagnostic-scope-and-safe-unavailable-result.md) 的危险升级／危险未明／安全能力不可用三分支完整保留；只把危险升级主人提示固定化，并增加仅在该分支成立的附加联系人警报。
- [Ticket 65](65-define-diagnostic-evidence-recipients-and-retention-boundary.md) 的最小证据、路线外查询禁令、最小危险事件与停止记录边界保留；支持联系人是独立的新健康资料接收方，不能继承模型首跳授权，新增内容严格受本票最小警报和留存边界约束。
- [Ticket 73](73-define-health-task-generation-dispatch-and-lifecycle-contract.md) 的范围批准、外部效果分层、未知不盲重试与删除边界保留；联系人警报不是普通任务，普通任务控制不能替代警报批准。
- [Ticket 75](75-close-first-release-health-steward-product-contract.md) 保留单人产品、主人安全结果、独立控制与真实验收要求，并新增本票联系人能力；无有效联系人不降低主人提示或阻断健康管家，但宣称联系人警报可用前必须验证实际配置路径。
- [Ticket 39](39-define-permanent-deletion-backup-promise.md) 的无倒计时、无删除后处理、无恢复和无本地审计例外继续成立；站外已收内容不在本地删除能力内。
- [Ticket 58](58-decide-health-model-recipient-lock-gap-boundary.md) 的模型首跳同意边界保留；支持联系人是另一类接收方，二者批准互不继承，也不能借联系人批准做路线外医学查询。
- [Ticket 74](74-confirm-owner-binding-message-admission-and-trust-boundary.md) 的唯一画像主人、唯一健康入口和可信准入边界保留；联系人只单向收最小警报，其回复不能进入画像、证据、任务或控制链。

这是实质新增的第三方接收方与自动外部效果，不是现有 HOW 的小型发送接口补丁。[Ticket 100](100-define-seven-health-skill-interaction-entry-document-and-capability-boundaries.md) 仍须先把该安全结果映射到七个 Skill；两张 TO 均闭合后，必须建立后继 CAN 能力链拆分 Ticket，完整重审最新 TO 对接收方授权、不可绕过安全触发、发送／未知／纠正、停止记录、删除和真实验收的能力要求，再修订受影响的统一 HOW。未受影响且证据仍当前的 CAN 事实可以明确继承；本票没有证明联系人能力已经实现、部署或可用。
