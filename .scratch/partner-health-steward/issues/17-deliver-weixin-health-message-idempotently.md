# 17 — 建立严格幂等的微信健康投递

**What to build:** 让健康状态提示、主动消息、私密查看和附件通过版本固定的 partner 微信适配层可靠投递，同一逻辑投递无论重试或进程恢复都至多发送一次，结果不确定时停止而不是盲目重发。

**Blocked by:** None — can start immediately

**Status:** resolved

- [x] 每次健康投递使用由 sidecar 任务或动作派生的稳定 delivery ID，不使用每次随机生成的发送身份作为幂等依据。
- [x] 无正文投递账本只保存投递 ID、接收身份、时间、状态和必要错误码，不保存健康消息或附件正文。
- [x] 相同 delivery ID 的重复请求、网络重试和进程恢复不会产生第二次微信投递，并能返回可复盘的既有结果。
- [x] 渠道已接收但本地状态提交失败、网络确认不确定和并发派发均不会触发盲目重发；不能证明安全重试时任务转为终态并触发无内容运维信号。
- [x] 文本消息和 JSON 附件均使用同一幂等语义；缺少严格 `send_once` 能力的旧发送入口对可重试健康投递失败关闭。
- [x] 适配层固定到已验收 Hermes 版本；版本不匹配时健康投递失败关闭，Hermes 升级必须重新通过兼容验收后才能启用。
- [x] 主验收覆盖成功、重复、并发、超时、已发送后落库失败和进程恢复，并只从微信网络确认、投递状态及无内容审计观察结果。

## Answer

新增 `sidecar/weixin_delivery.py`：以 sidecar delivery key 派生稳定微信
client ID，在受限 SQLite 账本中先登记再投递；文本与 JSON 附件共用同一
`send_once` 语义。微信确认不完整、进程中断、并发占用或微信已接收后本地
提交失败时均保持终态/不确定态，后续不会盲目重发。生产 transport 从指定
Hermes 源码根加载并暴露实际版本，版本不符时在建账和联网前失败关闭；派发器
也会保留“不确定投递”语义而不改写成普通可重试失败。

验证证据：微信投递定向测试 17/17 通过，另有 1 项真实审计存储幂等回归通过；
派发器定向测试 11 通过、1 项因本机 Windows 无 AF_UNIX 跳过；全量 343 项
通过、18 项为平台或环境能力跳过；
`compileall` 与 `git diff --check` 通过。关键成功/重复/并发/超时/恢复/落库与
审计故障场景均穿过生产 `HermesWeixinTransport`，只以可控微信网络返回、时钟
和审计故障替身代替外部边界；审计按稳定事件 ID 幂等写入，成功、不确定和拒绝
信号均可在恢复后补写而不重发微信。真实 DMIT 部署及微信联网验收仍由后续生产
部署 Ticket 完成，本结果不冒充已部署或已上线。
