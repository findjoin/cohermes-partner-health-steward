# 19 — 用当前画像和权威资料回答健康问题

**What to build:** 让健康相关微信轮次只获得当前必要画像和可追溯资料，画像刚更新时立即使用新版本；缺少新鲜资料卡时先明确核验并在受控时限内查询白名单来源，无法核验时诚实说明。

**Blocked by:** 16 — 让一条已同意的健康微信消息可信入档；17 — 建立严格幂等的微信健康投递

**Status:** resolved

- [x] 只有独立判别为健康相关的轮次临时注入当前 300 字画像、相关证据 ID 和资料卡摘要；普通聊天轮次不接收健康画像正文。
- [x] 当前消息产生画像写入时，后续健康回答使用新提交版本，而不是判别前的旧画像。
- [x] 自动判别和健康回答复用同一份独立固定健康模型配置；该配置作为日检和派发的共同契约，二者的生产 Job 装配与验收仍由 Ticket 23 完成。
- [x] 部署证明机制记录健康供应商、规范化端点、固定模型、隐私模式、认证档案和配置摘要，每次调用另行核对响应实际模型；不把第三方中转描述为官方或直连，真实 Linux 运行值与变更复验仍由 Ticket 14/15 留证。
- [x] 健康回答优先使用未过期资料卡；缺少卡片时先发送 `正在核验资料`，并给白名单资料下载最多额外 20 秒。
- [x] 白名单资料成功返回时才生成并采用新资料卡；不可用、超时或校验失败时明确说明无法核验，不扩展到任意网站，也不把模型记忆当作权威来源。
- [x] 外部资料始终作为不可信数据处理，不能调用工具、写入个人事实或直接创建派生任务。
- [x] 主验收从真实格式健康消息经过 production plugin、判别、最新画像、资料卡或受控下载到幂等微信回答闭合，并验证普通聊天不读取健康上下文、不调用健康回答模型。

## Answer

Ticket 19 已于 2026-08-09 完成本地实现。production plugin 现在把已同意且判为健康相关的微信轮次在普通文本合批前分流：候选写入后以一次性本轮收据读取 sidecar 当前画像，再通过同一份独立固定配置进行 fresh、无历史、无工具、无 fallback 的健康回答。请求显式绑定 provider、规范化 endpoint、partner auth profile 和 model；响应返回的实际 model ID 不一致时拒绝采用。分类一旦确认健康相关，后续签名、入档、上下文、资料或回答异常及超时均固定失败关闭，不再落入普通聊天。

资料路径优先使用新鲜资料卡；缺卡时先发送 `正在核验资料`，仅查询静态目录选出的精确 HTTPS 白名单 URL，并在 20 秒硬预算内成功校验后才写卡和用于回答。上下文、回答、资料和微信投递均有边界测试；重复本轮收据在第二次模型可见读取前被持久拒绝，微信最终回复继续使用稳定 delivery key。

验证证据：`python -m unittest discover -s ops\partner-health-steward\tests -v` 通过 435 项、跳过 23 项；跳过项均为当前 Windows Python 不提供 AF_UNIX 或 Linux peer-credential 的环境验收。真实 production-factory 主 seam 已写入测试并在 Linux 上可执行；本票不宣称真实 partner Linux 已部署或验收。实际 Unix socket/微信运行证据仍归 Ticket 14/15，日检与派发的固定模型及生产 ports 归已解阻塞的 Ticket 23。

两轴复审无 Ticket 19 剩余阻塞。既有的 classifier 会把受信封套身份字段交给固定健康模型并让模型回填候选来源字段，这是 Ticket 16 延续的隐私债，不是本票新增行为，后续应单独去标识并由 coordinator 注入受信字段。
