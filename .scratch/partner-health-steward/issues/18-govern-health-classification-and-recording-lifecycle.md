# 18 — 完善自动判别与停止记录生命周期

**What to build:** 让已绑定主人的每条微信消息都独立、限时地判断是否与健康相关，同时保证普通聊天不入档、故障不阻塞对话，并允许主人停止记录而保留现有加密档案和后续恢复权。

**Blocked by:** 16 — 让一条已同意的健康微信消息可信入档；17 — 建立严格幂等的微信健康投递

**Status:** resolved

- [x] 每条已认证主人消息使用一次独立 fresh 健康判别；普通聊天不创建候选、证据、画像版本或健康成功尾标。
- [x] 判别在 15 秒内未完成时普通 Hermes 回复仍可继续，并向主人显示 `记录处理中`，不得假称已经保存。
- [x] 精确可信入站信封最多保留十分钟并只重试一次；成功显示 `已补录`，第二次失败显示 `本次未记录`，随后清除重试材料。
- [x] 三类处理状态属于被动状态反馈，不计入滚动 24 小时的 100 条主动健康消息上限。
- [x] 除已接纳证据外，只在进程内保留同一主人的最近三条普通消息，最长 72 小时；进程重启后清空，不进入健康档案或普通 memory 投影。
- [x] 主人可通过新鲜动作收据进入 `recording_stopped`；系统随即停止新判别和写入、取消待重试判别与派生任务并暂停主动触达，但保留查看、导出、恢复和删除能力。
- [x] 恢复健康记录必须由主人当前轮明确发起；管理员、查看者、定时任务和模型推断不能自动恢复。
- [x] 主验收覆盖普通聊天、健康消息、判别超时、一次重试、重启清理、停止和恢复，并观察微信反馈、sidecar 状态、任务取消及无内容审计。

## Answer

- 微信适配层现在对每条已认证主人消息建立独立且总预算为 15 秒的健康判别；超时立即放行普通聊天并显示 `记录处理中`，进程内只保留最多十分钟的精确信封，且只进行一次新 attempt 重试。补录成功和最终失败分别通过固定、幂等的 `已补录` 与 `本次未记录` 状态反馈送出。
- 普通消息只进入进程内最近三条、最长 72 小时的临时窗口；重启清空。它不创建健康证据、画像版本、普通 memory 投影或成功尾标。
- sidecar 新增收据约束的 `recording_stopped` / `recording_enabled` 生命周期。停止会阻断新判别与写入、取消未完成的派生任务并暂停主动触达；恢复必须由当前主人使用新鲜的一次性动作收据发起。现有加密档案以及查看、导出和删除能力保留。
- 聚焦验收运行 84 项，其中 78 项通过、6 项因 Windows 缺少 Unix socket/受限账户能力跳过；全量健康管家回归运行 392 项，其中 371 项通过、21 项环境跳过。新增回归覆盖停止—入档、停止—日检快照/提交、阻塞资料下载不拖住停止且不得迟到写入或丢失吞吐计数/待处理候选、停止—派发失败并发，并发派发 claim 保护、独立主动暂停、排队及零延迟重试停止、attempt lease，以及首次已提交但响应丢失时的无内容确认；`compileall` 与 `git diff --check` 通过。
- 本结论只证明 Ticket 18 的本地实现与 Windows 可执行验收通过。真实 AF_UNIX、受限账户、微信渠道与 DMIT 部署验收仍属于后续 Ticket 14/15 的 Linux 门槛，未在本 Ticket 中宣称完成。
