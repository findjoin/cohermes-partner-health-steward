# 【TO】确定七个健康 Skill 的主人交互入口、文档结构与能力边界

Type: grilling
Status: resolved
Parent: [健康管家首发 TO、CAN 与 HOW 决策闭合路线](../map.md)
Blocked by: [【TO】确定健康 Skill 的必经使用、主人可见披露与回复结果](99-define-required-health-skill-use-visible-disclosure-and-reply-contract.md); [【TO】确定危险升级时主人提示、预设支持联系人通知、记录与失败结果](101-define-danger-escalation-owner-prompt-and-support-contact-alert-contract.md)

## Question

主人希望通过七个有清楚文档边界的 Skill 管理同一个健康管家，并能用自然语言或明确入口理解、启动和控制相应能力。当前 HITL 已确认以下七个拟议健康 Skill：

1. `health-init`：健康管家初始化；
2. `health-steward`：初始化后的健康管家总入口；
3. 健康画像维护；
4. 健康证据维护；
5. 主人询问；
6. 文献查找；
7. `health-settings`：初始化成功后，主人可明确发现并询问健康管家能设置什么、查看当前设置并提出修改意图的“健康管家设置” Skill；它仍通过 `health-steward` 协调，实际可设置范围必须由健康管家 Plugin 的主人产品能力决定，不能由 Skill 文档自行扩张。

主人已经确认第七个 Skill 为 `health-settings`，其产品目的不是保存健康事实或另建任务，而是让主人理解健康管家 Plugin 面向主人开放的设置能力、查看当前设置并提出修改意图。不能由 AI 把任务框架、安全门禁、某个现场文件或任意技术模块静默改名为 Skill。正式 Partner 当前存在的旧 `medical` 只作为冲突审计输入：它与健康管家在健康记录、问答和安全边界上有重叠，不能因文件存在就成为七个现行健康 Skill 之一，也不得与 `health-steward` 竞争健康消息。现行任务框架继续拥有任务目标、阶段、验收和四标签，安全边界继续由产品整体强制；除非主人通过具体场景改变这一产品决定，否则二者都不是额外 Skill。

在七个 Skill 名单确认后，本票用主人实际与 Hermes 对话的场景，逐一确定每个 Skill 文档必须表达的产品边界：

- **交互角色与主人目的**：先确认它属于 A“主人可以直接进入”、B“只能由 `health-steward` 协调，主人只看真实使用披露”，还是 C“仅提供说明或帮助”；再说明主人为什么会用它。B 或 C 类不得为了可发现而获得绕过 `health-steward` 的独立健康处理入口；
- **可发现入口**：主人可通过什么自然表达或明确入口找到 A 类 Skill，B/C 类怎样被解释或披露，哪些自动处理可以在什么前提下采用它；
- **启用前提与触发范围**：初始化前、初始化中、初始化后、暂停支持、停止记录、故障、迁移和永久删除后分别是否可用，什么信息属于它，什么信息必须交给另一 Skill 或产品结果；
- **允许读取与形成的结果**：可以读取哪类当前资料，可以提出问题、候选证据、画像变化、资料候选、任务建议或主人控制中的哪些结果；是否可以直接对主人说话，哪些内容只能提出候选，由谁确认并呈现权威结果；
- **主人可见回复结构**：主人看到的用途说明、处理结果、记录结果、任务结果、下一步、真实 Skill 使用标识，以及失败或无法确认时的固定结果；
- **记录与数据边界**：允许长期保存的最小 Skill 使用事实和受管业务结果，不得保存或复制的完整对话、Skill 正文、提示词、模型草稿和无关个人资料；
- **协作与越权边界**：每个 Skill 可以向哪个职责提交什么候选，不能自行修改什么，不能把“调用成功”冒充画像、任务、诊断、外部效果或主人收到；
- **禁止事项与交接条件**：初始化、健康问答、证据、画像、文献、任务、安全、用药、数据权利和普通聊天之间发生冲突时，必须停止、澄清、交接或失败关闭的条件。

至少用以下对照场景闭合，不先让主人确认抽象结构：

1. 未初始化时主人发送初始化请求，以及未初始化时直接说“我昨天没睡好”；
2. 初始化成功后主人自然说“我昨天没睡好”，本轮哪些 Skill 实际参与、分别形成什么结果；
3. 主人纠正一条既有健康资料，证据维护与画像维护各自能做什么、不能做什么；
4. 主人问一项一般健康知识，本地资料足够、资料不足以及主人要求实时搜索时分别发生什么；主人派生医学查询不得因此被发到当前获准首跳模型路线之外；
5. 健康管家准备建立、推进、延期或取消任务时，七个 Skill 与任务框架怎样分工；
6. 主人明确点名某个 Skill、只说自然语言、或系统内部认为需要某个职责时，主人如何看见真实入口和实际使用结果；
7. 主人查看或导出画像、暂停主动支持、停止新增记录、取消任务、撤回批准、查询运行状态或永久删除时，哪个 Skill 负责交互，哪些仍由产品整体权威处理；
8. 主人请求辅助诊断、出现危险信号、危险事实不足或安全能力不可用时，Skill 可以做什么，哪些结果只能由不可绕过的产品安全边界决定；
9. 旧 `medical` 与 `health-steward` 都可能匹配同一句健康消息时，怎样确保只有当前已确认的健康管家入口形成产品结果，避免初始化旁路、重复记录和竞争权威；
10. 必需 Skill 缺失、版本变化、文档边界冲突、使用事实无法证明，或业务结果已经提交但回复／微信交付未知时，主人分别看到什么。

本票只确定人机交互方法、七个 Skill 各自文档应承载的产品职责以及主人可见边界，不选择 slash、`skill_view`、模型自动选择、Adapter 路由、Tool、Command、文件路径、schema、数据库、hash、具体加载器或其他实现机制。Hermes 能否稳定发现、自动选择、确定性加载、组合并披露这七个 Skill，须由本票闭合后的 CAN 事实回答；HOW 才能选择最终入口与调用路线。

完成条件：主人通过上述具体场景确认七个 Skill 的最终名单、友好名称、规范名和 A/B/C 交互角色；每个 Skill 都形成一份不重叠的产品能力边界与统一文档栏目；形成一张“现行产品能力 → 主 Skill → 协作 Skill → 健康管家权威执行边界 → 主人入口 → 权威结果”的完整覆盖矩阵，逐项遍历初始化、画像、证据、健康问答、任务、复盘、主动支持、数据权利、运行状态、辅助诊断和安全结果，任何能力都不得遗漏、重复拥有或借 Skill 绕过权威执行边界；自然语言、明确入口、自动处理、真实使用披露、业务结果和主人收到保持为不同事实；旧 `medical` 的退出、彻底改写或其他处理结果明确；`CONTEXT.md` 同步技术无关的现行术语；本票形成唯一 `## Answer`。若本票改变现行完整产品功能、主人可见结果、失败结果或边界，后继 CAN/HOW 按 Map 规则重新闭合，但不得借此重复讨论未受影响的产品目标。

## Comments

### 2026-08-21 — HITL：确认总路由与四职责的协作关系

主人确认 `health-steward` 是初始化成功后全部健康处理的总路由与统一协调 Skill。主人自然健康消息和自动任务／复盘事件都先进入 `health-steward`；它结合当前处理目的、相关画像导航、相关主题与任务状态，决定本轮不调用、调用一个或按依赖顺序调用多个职责 Skill，并为每项职责限定本轮目的和所需最小资料。

主人确认四个职责 Skill 不直接互相拥有或推进彼此：它们把候选结果、缺口或交接建议返回 `health-steward`，再由 `health-steward` 决定下一步并组织主人回复。产品级依赖关系为：`health-owner-inquiry` 取得的主人回答先形成候选个人证据，`health-literature` 取得的资料先形成候选通用知识，二者均须交给 `health-evidence` 判断准入、纠正、撤回、失效及能够支持什么；只有当前已准入且适用的证据才能交给 `health-portrait` 更新受影响主题。`health-portrait` 或 `health-evidence` 发现缺口时，只把缺口返回 `health-steward`，由总路由决定是否再采用主人询问或文献查找。

主人确认这不是每轮并行调用全部四个职责，也不是让各 Skill 直接写入权威状态。非 Skill 的任务框架仍拥有任务目标、阶段、验收和四标签，健康管家权威执行边界仍确认最终证据、画像、任务、控制和其他业务结果；`health-steward` 只根据已确认结果组织一份主人可见回复，不能自行发明个人事实、准入证据、改写画像或完成任务。接下来先逐项对齐每份 Skill 文档，从 `health-steward` 的路由规则、输入、选择条件、返回处理和失败边界开始。

### 2026-08-21 — HITL：后续讨论顺序

主人规定后续不先讨论逐句话术，而按以下顺序闭合：先确定健康管家长期维护的逻辑文档／记录分别是什么及各自结构；再由这些结构推导每个 Skill 必需、可选与禁止取得的上下文，以及上下文如何取得；随后依据目标 Hermes 的真实上下文机制核验这些上下文怎样被加载和注入；最后才闭合各 Skill 的输出、交接与主人可见回复。讨论中不得把“一项 Skill”等同于“一份物理文件”，也不得在没有 Hermes 证据时猜测注入机制。

### 2026-08-21 — HITL：确认第七 Skill、文档分层、证据—画像依赖与上下文阶段边界

主人确认第七项为 `health-settings`。它是初始化成功后主人可明确发现的“健康管家设置”入口，用来说明这个健康管家 Plugin 面向主人实际开放哪些设置、展示当前设置并接收修改意图；明确调用仍进入 `health-steward` 的统一协调，不形成旁路。可设置内容必须在本票中根据健康管家的产品特性逐项闭合，不能从某个 Skill 文件、现有实现或通用 Hermes 设置反向推导。

主人确认采用两层文档：每个 Skill 有一份主合同文档，跨 Skill 的产品、安全、任务、数据权利和失败规则只保留一份并由各 Skill 引用；个人状态继续由共享的启用／设置／控制、证据、画像、任务、诊断／安全、运行／交付等逻辑权威记录承载，不因 Skill 拆分复制第二份状态。物理文件、数据库与加载方式尚未选择。

主人确认 `health-evidence` 与 `health-portrait` 的单向权威依赖，但增加必要触发条件：只有 `health-steward` 先判断本轮消息包含需要形成、核验、纠正、撤回或失效的证据候选时，才采用 `health-evidence`；证据候选经产品权威确认成为当前可用证据后，`health-steward` 才按实际影响决定是否采用 `health-portrait`。二者不默认每轮调用、不直接互相调用，也不复制同一正文。

主人确认先在本 TO 中冻结“每个 Skill 必须、可以和禁止取得什么业务上下文”的产品合同，再由后继 CAN 核验目标 Hermes 的真实取得、加载、版本绑定、隔离和披露事实，由 HOW 选择具体注入机制。此前为解释而举出的各 Skill 上下文清单尚未获得主人确认，不得当作本票决定；下一步从维护对象及其结构开始，再逐项推导上下文。

### 2026-08-21 — HITL：确认首版设置面与 Skill 文档栏目，暂缓上下文分配

### 2026-08-21 — Hermes Skill 文档分层事实核验

[Hermes 七个健康 Skill 的文档分层、加载与 token 成本核验](../evidence/29-hermes-seven-health-skill-context-loading-and-token-efficiency-20260821.md)确认：统一十二栏适合作为每个 Skill 的产品完整性审查表，但不应机械展开成七份等长运行正文。目标 Hermes 的常驻 Skill 索引主要依赖唯一规范名和短而有区分力的 `description`；完整 `SKILL.md` 在 `skill_view` 或显式 slash 路径中按需加载，多个 Skill 首次加载时复制的共享长规则会重复进入模型输入。运行主文档应保留该职责每次必须看到的触发／排除、上下文类别与缺失行为、步骤、候选结果、交回、禁止写入、停止及验证；共享结构、长规则和示例只保存一次并按需取得，动态主人状态不得写入 Skill。文档结构能够提高选择和执行准确性，但不能单独保证自然语言稳定调用；目标固定版本也没有可确认的 `auto_skill` 机制，当前 Partner 尚未部署这七个健康 Skill。具体普通 Skill／Plugin Skill、加载器、上下文注入和失败关闭仍由后继 CAN/HOW 处理。

### 2026-08-21 — HITL：确认长期资料、按需上下文与运行文档结构

主人确认长期真实资料以健康画像和健康证据库为核心，同时包括任务、设置与控制、诊断与安全结果、Skill 使用／处理／交付等不能塞进画像或证据库的受管事实。Skill 不自行任意浏览这些资料：`health-steward` 先确定本轮目的，通过索引定位相关对象，再由健康管家权威执行边界形成当前目的所需的临时只读上下文；Skill 返回候选，只有权威执行边界确认后才更新长期真实资料。索引只负责定位，实际被选中的 Skill 仍须取得完成职责所需的最小内容；上下文不是第二份画像、Skill 私有数据库或长期副本。

主人确认每个 Skill 使用一份精简主 `SKILL.md`：保留唯一名称／版本／短描述、选择与排除、前提、上下文类别与缺失行为、核心步骤、候选返回、硬边界、停止与验证。统一十二栏继续作为产品设计和验收检查表，而不是十二个必须逐字展开的运行章节；较长稳定结构、规则和示例按需引用，主人画像、证据、任务、设置、本轮消息及其他动态状态永不写入 Skill 文件。目标 Hermes 对普通 Skill 支持按需 supporting files、对固定版本 Plugin Skill 的 linked-files 能力不足，最终文件布局和加载路线留给后继 HOW；本 TO 只固定上述产品文档与上下文边界。

### 2026-08-21 — HITL：确认总路由分层上下文与证据职责触发

主人确认 `health-steward` 不在每轮读取完整画像，而采用分层取得：每次先取得当前主人消息或自动事件，以及初始化、当前控制、运行和安全能力等入口事实；只有涉及个人健康或健康任务时，才取得画像顶部当前状态、六域相关主题和开放任务的紧凑导航；总路由选择职责后，再为实际被选中的 Skill 取得完成当前目的所需的主题、证据卡或任务详情。设置、数据权利和运行状态等不需要画像判断的请求不得为了统一形式加载无关画像。

主人确认 `health-evidence` 只在本轮需要形成、核验、纠正、撤回、失效或重新判断证据能支持什么时采用。触发既包括主人新陈述、测量、转述医生结论、纠正／否认、候选通用资料和需要形成任务过程证据的结果，也包括画像更新、个体化回答或诊断前确有必要重核既有证据的当前性、适用性和充分性；纯设置、运行状态、单纯数据权利以及不涉及主人事实且现有合格通用知识足够的一般知识回答不调用。看见健康词本身不是触发条件。

主人随后指出：若按索引继续引用旧证据，必须明确旧资料哪些内容仍需保留、哪些可以压缩或清除，以及长期空间如何受控；不得把“可追溯”偷换成永久保存全部旧正文，也不得为了节省空间静默破坏画像、判断或任务的依据。该保留层级是下一项 HITL，尚未确认。

### 2026-08-21 — HITL 候选：按主题保留近期变化视图并将未回复纳入任务过程

主人提出一个尚待审计和确认的候选：只让能够影响健康画像的受管证据类别进入画像主题；每个标签展示最近五次对话中已经由证据证明的实际变化，更早内容压缩成有固定短长度限制的长期趋势；同一标签的主人对话间隔以三天为上限，并据此建立或派发健康任务。主人要求同时闭合任务已派发但主人没有回答时怎样记录。该候选当前不等于已确认产品合同；必须先区分“画像给主人看的近期变化窗口”与“证据库为追溯保留的最小历史”，并核验对话次数、固定字数和统一三天间隔是否有明确产品含义、是否会丢失重要依据或制造无目的催问。未回复本身不得在未判定前冒充个人健康事实。

### 2026-08-21 — HITL：修订 Q10—Q12 的证据有界目标

### 2026-08-21 — HITL：澄清容量未决并确认未回复可触发信息补全任务

主人指出，本票尚未讨论证据库的具体容量、达到容量时的产品结果或是否停止某类新增记录；此前解释中的“达到容量上限且无法安全压缩时停止该范围的新增长期记录并通知主人”不是已确认 TO，不能写入 Q10 决定。当前只确认证据库必须受限、允许 AI 提出压缩时机且须防止 AI 记烂账；容量以什么物理量计量、上限是多少、达到上限时怎样对主人呈现和处理，继续保持未决。

主人确认 Q12 的基本结果，并补充：当 AI 从当前画像、开放判断、任务验收或已确认送达但截至约定时间仍未收到回答的任务过程事实中发现一个具体且必要的信息缺口时，可以向任务框架提出“信息补全任务”候选。任务框架须先核验缺口、目的、关联判断、预期结果、主人当前控制和是否已有同一缺口任务，再决定建立或合并；`health-owner-inquiry` 只负责生成完成该缺口所需的最小、非诱导问题，不能自行建档、派发、重复催问或把任务标为完成。未回复只记录任务过程，不更新画像或健康趋势；消息交付未知时不得写成主人未回复，也不得据此自动重问。建立后任务保持 `active—等待主人`，主人回答且缺口被确认补足时才按任务验收完成，暂时无法回答可延期，明确拒绝或相关判断不再需要时可取消；明确危险情况不等待普通信息补全任务。

### 2026-08-21 — HITL：把容量问题前移为证据库结构，并把任务归入画像维护循环

主人进一步澄清：当前所谓“证据库容量”首先是证据库自身的逻辑结构问题，而不是先设卡片数、字节数或达限行为。证据库的产品目的，是为健康画像提供可追溯依据，并为以后实际采用 `health-evidence` 时提供能够定位、核验、准入、纠正、撤回、失效和压缩的受管资料结构；因此必须先确定证据怎样按画像主题组织、单条证据与历史摘要如何并存、哪些关系供画像和证据职责检索，再从结构推导保留容量。此前提出的具体容量与达限结果继续未决。

主人同时把健康任务放回同一画像维护循环：健康任务需要一套依据健康画像与证据库结构检索相关主题、证据、缺口和既有任务的流程，并由一个 Skill 判断当前目的需要检索什么；任务的根本产品目的应围绕维护健康画像，以及依据当前画像形成有理由的定时询问任务和建议任务。当前尚待具体场景确认：这个“判断检索什么”的职责是否由已确认的 `health-steward` 总路由承担，还是对现有七项 Skill 的职责另有调整；“维护画像”是仅指补充／更新画像，还是也包括依据画像向主人提供行动建议而不改画像；定时询问和建议是两类独立可验收任务、同一任务的不同阶段，还是仅为主人可见用途描述。在这些边界确认前，不新增第八个 Skill，不把每次询问、建议或 Skill 调用自动建成任务。

### 2026-08-21 — HITL：确认检索规划归总路由，并确认任务维护或应用画像

主人确认现有七个 Skill 已经足够，不新增检索 Skill。`health-steward` 负责根据本轮目的决定需要检索哪些画像主题、证据类型、时间范围、缺口、既有任务及排除项；健康管家权威执行边界执行受限取数并形成最小上下文，实际被采用的职责 Skill 只判断和返回自己职责内的候选结果。后续编写 `health-steward` 主文档时，必须完整保留这项检索规划职责，以及何时不检索、不得取得什么、资料不足时停止或追加受控检索的边界。

主人确认健康任务以健康画像为锚点，其根本目的包括维护画像，也包括依据画像向主人提供需要安排、跟踪或验收的支持与建议，即“维护或应用健康画像”。询问任务用于补足、复核或更新画像所需证据；建议只有需要后续安排、主人控制、状态跟踪或独立验收时才形成建议任务，一次即时建议仍可只是回答。询问、证据准入和画像更新通常是同一任务的阶段，不因每次 Skill 调用分别建任务。任务的具体触发条件须在证据库结构和检索合同确认后继续对齐。

### 2026-08-21 — HITL：确认六域固定导航与证据库的广义支撑边界

主人确认继续采用现行健康画像的顶部“当前状态”、六个固定一级领域及其固定基础二级主题，不在本票重画另一套画像分类。六域依次为临床与安全事实、身体功能与主观身体体验、心理／认知与主观福祉、活动与社会参与、健康行为与相关暴露、主人目标／价值与健康或照护偏好；固定二级主题沿用现行 TO，新增、改名、合并或删除仍须先说明用途并取得主人同意。

主人确认：健康证据库以同一六域及二级主题作为主要导航索引，为健康画像及画像驱动的问答、判断和任务提供同一套可追溯依据，而不只服务画像更新或某一项 Skill。个人健康证据、通用权威知识、任务过程证据继续是不可自动互换的三类；同一证据只保存一张权威卡，可以链接多个主题和结果但不复制正文。个人证据可以在准入后支持画像；通用知识不能证明主人事实；任务过程只能证明任务或产品发生了什么。下一步据此确定最小证据卡、关系与历史摘要结构，再闭合任务触发条件和证据保留容量。

### 2026-08-21 — HITL：确认健康任务采用候选触发与建档门槛

主人确认健康任务不由单一事件直接创建，而采用“候选触发 → 条件核验 → 建立、合并或不建立”的产品流程。主人明确健康目标、新准入证据变化、证据纠正／冲突／撤回／失效、影响当前理解或行动的画像关键未知、每日复盘、既有任务复查点、已确认送达但截至约定时间未回复，以及依据当前画像形成且确需安排、控制或独立验收的建议，都可以使 `health-steward` 提出任务候选。任务框架只有在能够定位可追溯依据、画像主题／开放判断／主人目标、明确目的、预期结果、承担者、允许资料／接收方／外部效果、推进条件或时机、可判定验收、当前控制与授权，并完成同缺口或同目标查重后，才能建立或合并任务。

定时器到点、出现健康词、Skill 被调用、画像主题空白、搜索命中、任务 `solved` 或 AI 仅仅觉得值得关注，均不能单独建任务。当前可信个人证据满足既有危险升级条件时直接进入“危险升级”；必要安全能力正常但缺少会改变立即行动的关键事实时进入“危险未明”；必要安全组件、来源或校验无法可信工作时进入“安全能力不可用”。这些安全结果优先于普通任务，且安全规则没有命中不等于已经证明安全。任务候选和实际建档、内部阶段与独立任务、接口接受与主人收到继续保持为不同事实。

### 2026-08-21 — HITL：确认一库三类并澄清证据职责、准入提交和主题索引

主人确认继续在一个逻辑健康证据库中保留个人健康证据、通用权威知识、任务过程证据三类强分型，并让它们采用共同证据卡骨架和各自不同的准入、适用与证明范围。主人随后要求澄清证据准入由谁判断和提交、三类证据与每个画像主题怎样对应，以及证据库究竟由哪个 Skill 管理。

现行职责边界按本票此前决定继续成立：`health-steward` 判断本轮是否需要证据处理、给出目的与最小检索范围；`health-evidence` 对候选内容提出类型、准入／拒绝／待澄清、当前适用性、不确定性、主题链接、支持／反对／限定、纠正／撤回／失效等结构化候选；无论候选为准入还是拒绝，都返回 `health-steward`，并由健康管家权威执行边界核验当前版本、引用、控制和冲突后才提交或保持不变。`health-evidence` 不直接写证据库，也不能把自身返回冒充权威准入结果。提交成功后，`health-steward` 再按实际影响决定是否采用 `health-portrait`；资料不足时可采用 `health-owner-inquiry`，通用知识缺口在既有边界内可采用 `health-literature`。

六域及固定二级主题是证据库的导航索引，不是每个主题必须预建“个人／通用／任务过程”三个空证据槽。每个画像主题本身存在并可明确显示未知；该主题可以链接零张、一张或多张不同类型证据卡，同一卡可链接多个主题但只保存一次。没有某类证据时查询结果为空，“没有证据”本身不能伪造成一张证据卡或健康事实。个人证据可以支持个人画像理解；通用知识只能支持解释、规则或建议，不能证明主人事实；任务过程只能证明任务或产品过程，不能证明健康变化。证据库的逻辑维护职责属于 `health-evidence`，实际唯一写入、引用完整性与版本提交属于健康管家权威执行边界；`health-steward` 负责协调而不取代这两者。

此前证据库方案只完成了“一库三类、六域主题索引、一证据一权威卡、多主题只链接、Skill 只产候选、核心提交”这些边界；历史摘要怎样替代旧明细、哪些证据不可有损压缩、证据卡最小共同字段、被拒绝候选是否及如何留存，以及物理容量与达限结果仍未闭合，不能称整套证据库管理方案已经完成。

### 2026-08-21 — HITL：撤回证据 Skill 直接写入，并澄清权威执行边界

主人明确撤回“`health-evidence` 判断准入后可以直接写入证据库”的候选说法，确认无论其判断是准入、拒绝、待澄清、纠正、撤回还是失效，都必须先返回 `health-steward`；总路由再根据该候选决定是否请求权威提交、采用 `health-portrait`、采用 `health-owner-inquiry`、处理通用知识缺口或只形成主人回复。`health-steward` 的路由决定本身仍不是证据已经写入。

### 2026-08-21 — HITL：确认每个画像主题固定展示三类证据列表

主人确认每个固定画像二级主题下都采用个人健康证据、通用权威知识、任务过程证据三个固定列表。每个列表可以没有证据，也可以链接多张证据卡；空列表只表示当前没有该类证据，不创建空白或占位证据卡。同一证据仍只保存一张权威卡，关联多个主题时只增加链接而不复制正文。此前讨论中的 `0..n` 只是“可以没有，也可以有多条”的关系缩写，不进入主人界面或 Skill 产品文案，也不表示证据库容量无限；历史压缩、保留和实际容量仍是后续未决项。

### 2026-08-21 — HITL：确认证据卡复用链接并纠正“最新证据等于主题状态”

主人确认 Q23：证据卡是健康证据库中只保存一次的权威元素，健康画像不复制其正文，而通过四类可追溯关系复用——主题链接表示与哪些画像主题相关；证明链接表示支持、反对或限定哪项具体当前理解；使用链接表示哪些任务、问答、诊断或安全结果实际采用它；历史链接表示证据之间的纠正、替代、撤回或摘要关系。这些关系应能从证据卡反向找到受影响结果，以便证据纠正、撤回或失效时重判；主题相关本身不等于已经证明某项当前理解。

| Skill | 必需或按需取得的最小上下文 | 只允许形成的结果 | 禁止与交接 |
|---|---|---|---|
| `health-init` | 当前未初始化／本次待完成状态、获准披露、资料与接收方边界、预置联系人及联系方法、时区和开放的初始偏好 | 固定说明必须展示具体联系人、联系方法、危险升级时自动最小警报的作用和“预置不等于授权”；另形成当前进度与下一必要问题 | 不读初始化前健康聊天或已删除旧状态；只有主人完成整体启用同意且权威提交成功，联系人警报批准和健康管家启用结果才能成立 |
| `health-steward` | 当前消息／自动事件、启用与控制、安全入口事实；按目的取得相关画像导航、主题、证据、任务和设置最小投影 | 本轮目的、检索与职责计划、提交请求、任务候选和唯一回复候选 | 不默认读取整份画像／证据库，不把候选说成已记录；所有职责结果回到这里协调 |
| `health-settings` | 当前启用状态、实际开放的设置与独立控制、数据权利、运行状态；按意图取得相关任务或联系人最小状态 | 可设置范围、当前值、修改／控制意图及影响候选 | 不读无关健康正文；只有对应权威能力确认后才能说已生效 |
| `health-portrait` | 受影响主题当前视图、相关已准入证据及证明关系、相关任务；确有跨主题影响才追加相邻主题 | 当前理解／未知、趋势、开放判断、关键未知及其依据的更新、维持、降级、撤回或缺口候选 | 不读未准入候选、完整聊天、无关主题或整库；只返回 `health-steward`，不写画像 |
| `health-evidence` | 原子候选、真实来源性质、时间、用途、相关既有卡与当前使用关系；压缩时才追加对应序列、近期窗口、保护关系和摘要谱系 | 准入／拒绝／待澄清、适用性、不确定性、证明边界、关系、纠正／撤回／失效／压缩候选 | 不读完整画像、聊天／上传副本或搜索堆；只返回 `health-steward`，不能直接写证据库 |
| `health-owner-inquiry` | 一个具体必要缺口、目的、相关主题最小理解、直接相关证据、任务验收、当前控制和同缺口已有询问状态 | 一个最小、非诱导问题 | 不读完整画像或诱导诊断；回答仍是候选个人证据，须回到证据链 |
| `health-literature` | 明确知识缺口、用途、允许资料与接收方边界、已有合格知识；确有需要才取得最小个人约束 | 带来源、版本、适用边界与限制的候选知识，或没有合格资料 | 不读取整份画像、不保存搜索堆、不把主人派生查询发到获准路线之外；长期采用须再经证据链 |

四个 B 类职责不直接互相调用、不直接回复主人、不写入证据／画像／任务、不发送外部效果，也不完成任务。任何必要资料缺失时，只返回明确缺口或停止。`health-evidence` 的判断也必须先返回 `health-steward`；只有权威执行边界完整提交成功才成为证据卡，之后 `health-steward` 才按实际影响决定是否采用 `health-portrait`。

### 五、画像、证据、任务与设置的共享结构

- 健康画像继续采用顶部“当前状态”以及临床与安全事实、身体功能与主观身体体验、心理／认知／主观福祉、活动与社会参与、健康行为与相关暴露、主人目标／价值／健康与照护偏好六个一级领域及既有固定基础二级主题。每个二级主题只有一份当前视图：当前结论或明确未知最多三条、开放判断最多三条、关键未知最多三条，每条最多 60 个中文显示字符；趋势同时一条且标题最多 20 个中文显示字符；任务和三类证据各预览三项，超出显示“另有 N 项”。显示预算不能靠截断改变语义。
- 证据库是一个逻辑权威层，元素是个人健康证据、通用权威知识、任务过程证据三类原子证据卡。每张卡只保存一次，通过主题、支持／反对／限定、实际使用及纠正／替代／撤回／摘要四类关系复用。每个可比较序列常规保留最新五张明细，受当前画像、任务、诊断、安全、冲突或纠正保护的卡额外保留；窗口外至少三张合格旧卡才可形成同类型历史摘要。摘要可以滚动形成后继，但不得抹去真实转折、例外、不确定性或谱系，完整提交后才能移除被替代明细。
- 待澄清候选在权威证据库之外随当前处理或信息补全任务临时保留，不能支持画像；拒绝、撤回、取消或不再相关后清除健康正文，只留无健康正文的最小处理事实。
- 健康任务候选只从三类检查提出：主人明确目标或动作请求；受管画像与证据状态复核；既有任务状态事件。候选仍须具备可追溯依据、画像锚点或主人目标、具体目的、预期结果、承担者、允许资料／接收方／外部效果、推进条件、可判定验收、当前控制／授权和查重，才由任务框架建立、合并或不建立。消息到达、定时器、Skill 使用、主题空白或 AI 泛泛认为值得关注都不能单独建任务。没有全局固定三天或七天；复查时间由具体任务目的、变化速度、主人负担和验收条件决定。
- `health-settings` 首版覆盖四组可见入口：时区、联系时间、表达方式、主动联系偏好与五类普通通知偏好；暂停主动支持、停止新增记录、任务取消、执行批准等相互独立控制；查看、纠正、导出、永久删除与运行状态；以及只能查看或在边界变化时重新说明、重新同意的资料范围、首跳接收方与启用状态。它同时覆盖危险支持联系人、联系方法、警报可用与批准状态，以及专门暂停、撤回和更换，但不能把这些控制合并成一个模糊“关闭”。时区变更必须显示生效时间；每日复盘从新时区的下一个有效当地自然日继续，不补做、堆积或重复旧日复盘。

这里的“容量管理”只固定逻辑收敛和资料生命周期，不选择卡、字节、文件或磁盘配额。物理计量、阈值、监控和存储实现属于 CAN/HOW；任何权威写入若不能完整提交，沿用既有失败／无法确认合同，不得部分写入、静默删除旧依据或声称已经记录，因此不存在待本票继续决定的容量专属主人结果。

### 六、完整能力归属

| 产品能力 | 主人／自动入口 | 主 Skill 与协作 | 不可绕过的权威结果 |
|---|---|---|---|
| 初始化 | 主人明确请求 | `health-init` | 初始化全部条件与启用提交 |
| 日常健康问答 | 两级路由 | `health-steward`，B 类按需 | 受管回复及真实记录结果 |
| 证据维护 | 健康消息、纠正或复核 | `health-steward` → `health-evidence` | 证据准入、拒绝、纠正、失效或摘要提交 |
| 画像维护 | 证据变化或明确查看／纠正 | `health-steward` → `health-portrait` | 画像修订、维持、降级或撤回 |
| 一般健康知识 | 两级路由 | `health-steward`；缺口时 `health-literature`，长期采用再用 `health-evidence` | 仅使用获准知识形成回答或明确资料不足 |
| 任务／每日复盘／主动支持 | 主人目标或自动事件 | `health-steward`，B 类按需 | 任务框架建档、合并、阶段、验收和四标签 |
| 设置／联系人／独立控制 | 主人表达 `health-settings` 意图后进入统一路由 | `health-steward` → `health-settings` | 对应设置、批准或控制的真实提交 |
| 数据权利 | 主人明确请求 | `health-steward` → `health-settings`；纠正时按需证据／画像 | 查看、纠正、导出、停止记录或永久删除结果 |
| 运行状态 | 主人明确请求或关键转换 | `health-steward` → `health-settings` | 活跃、异常或无法确认的派生状态 |
| 辅助诊断 | 两级路由 | `health-steward`，职责按准入范围参与 | 范围、安全和诊断修订边界最终决定 |
| 危险升级／联系人警报 | 正常由 `health-steward` 路由安全分支 | 职责不得延迟；证据纠正时可按需采用 `health-evidence` | 非 Skill 安全边界裁决并直接执行固定主人提示、最小警报／纠正与交付状态 |

联系人回复不进入任何 Skill、画像、证据、任务或控制链。支持联系人不是第二主人、健康入口或核心健康资料权利主体。

### 七、主人回复、真实使用与失败分层

每次主人回复按“直接结果 → 实际发生或未发生的记录／画像／任务／设置／外部效果 → 限制、失败或未知 → 必要下一步或一个最小补问”组织，最后由系统按可证明事实追加实际使用的 Skill 清单。内部路由计划、职责原始候选、Skill 正文、提示词和模型草稿不显示。

Skill 被找到、全文被加载、候选形成、权威提交、使用事实、发送尝试、接口接受和主人／联系人实际收到是不同事实。提交前必需 Skill 缺失或版本冲突时，对应普通业务结果不形成；能证明未提交时如实说明没有记录。业务已经提交但使用披露或微信交付无法确认时，业务结果仍成立，只把披露／交付标为无法确认且不重做。权威提交本身无法确认时，显示“处理结果无法确认”，不猜测成功或失败，也不盲目重试。最低安全结果是唯一 Skill 不可用例外。

### 八、代表性场景验收

| 场景 | 已确认结果 |
|---|---|
| 未初始化请求／健康陈述 | 明确初始化请求只用 `health-init`；普通健康陈述不触发健康处理或记录 |
| “我昨晚没睡好” | `health-steward` 按需采用证据，再按实际影响采用画像；只记录一次主观体验，不补写时长、趋势、诊断或自动任务 |
| 纠正旧资料 | 先形成证据纠正关系，再重判画像、任务与判断；不原位覆盖历史 |
| 一般知识／资料不足／实时搜索 | 合格本地资料足够就回答；缺口才用资料职责；没有合格资料就说明不足；不得扩大主人派生查询接收方 |
| 建立、推进、延期或取消任务 | `health-steward` 只提候选，任务框架按统一门槛建、并或不建；步骤不自动变成新任务 |
| 自然语言、明确点名、自动事件 | 都遵守同一产品结果；点名 B 类不旁路，自动事件不因无主人当前会话而降低门槛，只披露实际使用 |
| 设置、数据权利和运行状态 | 只取相关最小状态，经 `health-settings` 候选与对应权威能力形成成功、未生效、失败或未知结果 |
| 诊断、危险、危险未明、安全不可用 | 正常由 `health-steward` 路由，非 Skill 边界最终裁决；固定安全结果不被 Skill 延迟 |
| 旧 `medical` 竞争 | 无论被点名、自然匹配还是 steward 故障，都不形成现行健康结果或回退 |
| Skill 缺失／版本冲突／交付未知 | 提交前失败则不形成业务结果；提交后披露或交付未知不重做；提交未知不猜测、不盲重试 |

### 九、阶段影响

本票不选择 slash、`skill_view`、分类器、Adapter、Tool、Command、Plugin Skill、文件路径、schema、数据库、加载顺序、上下文注入方式或实际发送通道，也不声称七个 Skill 已经部署。由于前述 Skill 必经使用、七项交互和危险支持联系人三项后继 TO 已实质改变完整产品的交互、接收方、安全和失败合同，先前 CAN 闭合与统一 HOW 不再足以作为当前完整权威；下一步必须针对最新完整 TO 重建 CAN 能力链，逐项把旧 C01—C17、证据和 HOW 分类为可继承、需重查或已失效，再决定需要哪些调查与后继 HOW。实施与验收 Spec 在该权威链重新闭合前继续暂停。
