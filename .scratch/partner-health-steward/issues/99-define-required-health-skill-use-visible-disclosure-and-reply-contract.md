# 【TO】确定健康 Skill 的必经使用、主人可见披露与回复结果

Type: grilling
Status: resolved
Parent: [健康管家首发 TO、CAN 与 HOW 决策闭合路线](../map.md)
Blocked by: [【TO】闭合首发健康管家的完整产品合同与成功条件](75-close-first-release-health-steward-product-contract.md)

## Question

在不改变单人专用 Hermes、初始化完成后才启动、一个受管健康画像以及现有健康安全与数据权利边界的前提下，健康管家是否还必须形成以下主人可见产品合同：初始化的首次进入、中断后继续和永久删除后的空白重新初始化，都必须实际使用当前获准的初始化 Skill，而不是仅复制类似说明；初始化后的日常健康处理必须实际使用健康管家 Skill，并只在确有需要时使用相应职责 Skill；主人能够从系统产生而非 LLM 自述的标识看见本轮实际用了哪些 Skill？

本票必须用至少五个具体场景闭合这一项产品结果：

1. 主人首次进入初始化，初始化 Skill 成功使用，但初始化内容尚未完成；
2. 初始化成功后经历正常重启、经过验证的迁移或永久删除；
3. 初始化 Skill 缺失、加载失败、版本无法确认或无法证明本轮实际使用；
4. 初始化完成后主人说“我昨天没睡好”，健康管家 Skill 已使用、职责 Skill 使用或未使用；
5. 健康结果已经形成，但 Skill 使用标识或微信交付结果无法确认。

每个场景都要确认：哪些 Skill 是本轮产品结果的必需前提；主人看见的固定友好名称、规范名和使用标识；Skill 使用、初始化完成、健康结果形成、接口接受与主人真实收到如何保持为不同事实；Skill 或可见披露失败时是否停止初始化或健康处理；允许长期保存的最小使用事实；哪些内容可以由版本化 Skill 与模板决定，哪些结果必须由确定性产品状态决定。七个 Skill 的最终名单、完整人机交互入口、逐项文档结构、逐字回复及版本变化中的恢复交互由后继[【TO】确定七个健康 Skill 的主人交互入口、文档结构与能力边界](100-define-seven-health-skill-interaction-entry-document-and-capability-boundaries.md)闭合，不在本票形成竞争决定。

本票只决定产品必须做什么以及主人看见什么，不选择 Hermes slash、`skill_view`、Adapter 回调、配置字段、文件路径、hash 算法、数据库或其他实现机制。当前 Hermes 与微信是否能可靠实现这些结果，须在本票闭合后由后继 CAN 重新审计；具体实现组合再由后继 HOW 选择。

完成条件：主人以具体初始化和日常对话场景确认 Skill 必经使用、真实披露、启用持续性、失败分层和最小留存合同；`CONTEXT.md` 记录技术无关的“健康 Skill 使用事实”和主人可见结果；本票形成唯一 `## Answer`，并明确判断这是实质新增 TO，还是现行 TO 的等价解释。完整交互模式由后继七 Skill TO 闭合后，再统一判断对 CAN/HOW 的影响，不另建竞争 HOW。

## Comments

### 2026-08-20 — HOW 验收暴露的产品合同缺口

主人在验收现行技术路线时明确指出：初始化 Skill 应在初始化时实际使用并保障流程可靠性，日常健康回复也应如实显示所使用的健康管家 Skill；不能只由 Adapter 复制 Skill 说明，也不能由 LLM 自称调用。现行 TO 只确认产品规则与能力由权威文档和 Skill 承载、初始化入口可发现、初始化完成前健康管家不启动，尚未确认“每轮必须真实使用哪些 Skill、主人如何看见、使用无法证明时得到什么结果”。

当前事实已经足以说明这不是一次泛化 CAN 调查：Hermes 显式 Skill 入口、按需 Skill 加载、微信不原生显示工具进度以及现有披露只覆盖特定成功调用的边界均已有固定源码和现场证据。真正缺少的是主人对上述产品可见合同的决定；在本票闭合前，现行统一 HOW 不得进入实施与验收 Spec。

### 2026-08-20 — HITL 第一轮：初始化只执行一次并形成持久启用状态

主人纠正“每轮初始化都使用 `health-init`”的表述：`health-init` 不是每轮健康消息或初始化对话都重复调用；每个 Hermes 只有在实际使用初始化能力并成功完成初始化后，健康管家才启用，此后保持已启用。后续健康处理依赖并验证这一持久启用事实，而不是重复执行初始化 Skill。

主人同时确认第一轮其余方向：初始化后的健康处理应实际使用健康管家 Skill；职责 Skill 只在实际使用时披露；主人看到的 Skill 使用标识必须由系统根据真实使用事实产生，不能由 LLM 自述；无法证明某项当前必需 Skill 已正确使用时，不得把对应初始化或健康处理冒充成功。迁移到另一台 Hermes、永久删除后的空白重建、启用事实损坏或无法确认，以及初始化中断后怎样继续，仍需用后继场景区分后才能形成最终 Answer。

### 2026-08-20 — HITL 第二轮：迁移、可见披露与失败分层

主人确认正常迁移与永久删除必须分开：已经启用的健康管家完整迁移到另一台 Hermes 时，只校验并继承原初始化事实，不要求主人重新初始化或重复同意；继承事实无法验证时保持不可用。永久删除后旧初始化事实不再存在，主人以后主动建立空白健康管家时必须重新使用 `health-init` 完成初始化。

主人确认逐轮显示真实 Skill 使用清单：实际使用初始化 Skill 的那一轮显示 `🩺 本轮使用：健康管家初始化（health-init）`；初始化后的日常健康处理实际使用健康管家 Skill时显示 `🩺 本轮使用：健康管家（health-steward）`；本轮确实使用职责 Skill 时一并列出，未使用则不显示。后续日常消息不得重复显示 `health-init` 来冒充本轮调用；详细版本信息不占用日常回复，只在主人查询时提供。上述标识必须来自系统可证明的使用事实，不能由 LLM 自述。

主人确认失败结果分层：处理前无法证明当前必需 Skill 已正确使用时，不形成初始化或健康结果；Skill 使用及业务结果已经确认提交、但 Skill 尾注或微信发送结果未知时，已经提交的业务结果仍成立，只把披露或交付标为无法确认，不盲目重做，也不把它误报成“没有使用 Skill”。

### 2026-08-20 — HITL 第三轮：启用持续性、回复职责与最小留存

主人确认初始化成功形成的是持续启用事实：它跨正常重启和经过验证的迁移继续成立；暂停主动支持、停止新增记录以及暂时的能力故障不把产品改回“未初始化”。故障可以让运行状态变为异常或无法确认并停止受影响处理，但不删除初始化事实；永久删除才清除该事实，之后空白重建必须重新初始化。

主人确认初始化与日常回复采用不同表达合同：初始化说明、提问和关键结果由 `health-init` 中版本化的固定文案与模板决定，再由权威状态填入当前进度和下一步，LLM 不得改写关键披露或自行宣布启用；初始化后的日常健康回复可以自然表达，但必须遵守实际使用的 `health-steward` 与相应职责 Skill，并由系统独立追加真实 Skill 清单。

主人确认长期只保留最小 Skill 使用事实。初始化保留 Skill 规范名、版本指纹、使用时间、披露版本及其对应的启用结果；日常健康处理只保留与受管健康结果关联的实际 Skill 名与版本，不保存 Skill 全文、提示词、模型草稿或完整回复。

### 2026-08-20 — 后继七 Skill 人机交互合同已单独出票

主人要求修正健康 Skill 的 TO 规则，并另外用一张 TO Ticket 对齐主人如何通过七个 Skill 与 Hermes 交互、每份 Skill 文档应承载什么以及彼此不能越过什么边界。该问题已经作为[【TO】确定七个健康 Skill 的主人交互入口、文档结构与能力边界](100-define-seven-health-skill-interaction-entry-document-and-capability-boundaries.md)单独出票，并由本票阻塞。

本票继续只闭合“初始化实际使用一次并形成持续启用事实、初始化后按实际需要使用健康 Skill、系统如实披露使用、失败与交付分层以及最小留存”；七个 Skill 的最终名单、`medical` 是否作为第七个、每项文档结构及完整交互方法由后继票决定，二者不建立竞争 Answer。

## Answer

健康管家初始化必须实际使用当前获准的初始化 Skill，不能由 Adapter 复制相似文字或由 LLM 自称调用来代替。`health-init` 的成功使用只是初始化前提，不等于已经启用；只有既有初始化合同的全部步骤和权威提交都成功后，才形成持续的“健康管家已启用”结果。后续日常健康消息不重复调用或显示 `health-init`。

启用事实跨正常重启和经过验证的完整迁移继续成立，不要求主人重复同意或初始化；继承事实无法验证时，健康管家保持不可用，但不猜成未初始化。暂停主动支持、停止新增记录或暂时故障也不清除启用事实，只影响当前运行状态和受影响处理。永久删除才清除启用事实，主人以后主动建立空白个人状态时必须重新使用 `health-init` 完成新的初始化。

初始化后的健康处理必须实际使用 `health-steward`；画像维护、证据维护、主人询问、文献查找等职责只有在本轮确实参与时才列入使用事实，未使用不得显示。实际使用初始化 Skill 的回复显示 `🩺 本轮使用：健康管家初始化（health-init）`；初始化后的日常健康处理显示 `🩺 本轮使用：健康管家（health-steward）`，并按真实参与情况追加职责 Skill。标识必须由系统根据可证明的使用事实产生，LLM 不能自行书写或补报；详细版本只在主人查询时提供。

必需 Skill 在处理前缺失、加载失败、版本或实际使用无法证明时，不形成对应初始化或健康业务结果。若 Skill 使用和业务结果已经确认提交，而使用标识、回复发送或微信交付结果无法确认，已提交的业务结果仍然成立；未知只属于披露或交付，系统不得盲目重做，也不得谎称没有使用 Skill。

初始化的关键说明、提问和结果结构来自版本化 `health-init` 文档与模板，由权威状态填入当前进度和下一步；LLM 不得改写关键披露或自行宣布启用。日常回复可以自然表达，但必须遵守实际使用的 `health-steward` 和职责边界，真实使用清单由系统独立追加。初始化长期只保存 Skill 规范名、版本指纹、使用时间、披露版本和对应启用结果；日常只保存与受管业务结果相连的实际 Skill 名与版本，不因披露而长期保存 Skill 全文、提示词、模型草稿或完整回复。

本票是对现行“初始化后才启动、权威规则和能力由文档与 Skill 承载”的等价澄清：它把必经使用、可证明披露和失败分层说清，没有新增独立健康功能。因此本票本身不触发完整 TO—CAN—HOW 重跑；它暴露的确定性加载、版本绑定和微信真实披露事实，连同后继[【TO】确定七个健康 Skill 的主人交互入口、文档结构与能力边界](100-define-seven-health-skill-interaction-entry-document-and-capability-boundaries.md)最终确认的交互合同，在后继 TO 全部闭合后由一张聚焦 CAN 统一核验，再修正原统一 HOW，不建立竞争路线。
