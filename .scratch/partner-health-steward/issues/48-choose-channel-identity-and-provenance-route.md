## Question

在“核验微信 iLink 与目标 Hermes 的真实接口能力”给出的官方保证、固定源码行为、目标现场事实、未验证项和获准实验边界内，选择微信作为当前首发接口时的主人授权、逐条来源、重复投递、普通聊天交接、回复与恢复路线；该路线如何满足已经确认的产品边界，并对接口无法保证或尚未验证的部分保留真实的不确定性，而不把猜测写成接口事实？本票只在 CAN Research 解决后选择 HOW。

### 2026-08-16 — 接口 Research 纠正（发生在 Grilling Round 6 之后）

[微信 iLink 入站接口与重复投递语义核验](../evidence/07-weixin-ilink-inbound-contract-and-replay-semantics-20260816.md)确认：iLink 通过 `getupdates` 返回消息数组和同步游标；单条消息可以携带 `message_id`、`seq`、协议时间、item 级 `msg_id` 等字段，但腾讯官方类型把它们定义为可选，也没有公布重复投递时这些值是否稳定。目标 Hermes 只使用顶层 `message_id`，并额外用“发送者 + 正文”做 300 秒去重；已合并上游证据又表明同一逻辑消息可能带不同 `message_id` 重投。因此 Round 6 的“不得仅凭正文相同吞掉主人有意重复发送的消息”继续作为产品意图；“不同 ID 必定是两次独立主人动作、只有相同 ID 才是重复”这一传输层推断撤回，不作为当前接口事实。

当前只锁定：健康接入必须在任何正文去重或合批之前保留每个 iLink envelope 的全部可用来源字段和独立 Hermes 接收时间；缺失字段必须如实标记，不能伪造可信微信 ID。怎样消除疑似重投歧义、怎样持久化和恢复，留在本票后续 HOW 与获准后的真实微信元数据验证中。本次研究不新增 TO 选择，也不把 Ticket 48 标为已解决。

### 2026-08-16 — Grilling Round 2

主人确认采用双层结构：健康 Plugin 的接入保护始终执行，负责不可跳过的身份、逐条来源与失败关闭边界；同一能力包同时提供一个普通、可发现的 Health Skill，其名称与简短说明进入 Hermes 的技能索引，由同一个 Hermes 判断相关时按需加载完整说明并调用健康 Plugin。Hermes 可以决定是否展开详细健康流程，但不能决定是否执行接入保护。健康推理继续使用该 Hermes 当前受支持的模型能力，不新增独立模型、provider 或 LLM Gateway。仅通过 `register_skill` 注册且不进入普通技能索引的 Plugin Skill，不能单独实现这项自主发现要求。

### 2026-08-16 — Grilling Round 3

主人接受“预先指定 + 本人接受”的首次绑定：上线者只把当前真实主人的微信私聊身份预先指定为唯一待绑定身份；进入技术白名单或最先发来消息都不自动取得健康档案主人身份。只有该身份本人完成既定知情启用与恢复准备后才激活为当前唯一主人；其他身份、群成员、管理员、操作者和服务器所有者均不能抢占或代办。激活完成前不得创建、读取或修改个人健康档案。

### 2026-08-16 — Grilling Round 4

主人接受首发整条拒绝边界：来自当前已激活主人以外的微信私聊身份或任何群聊的消息，都在交给 Hermes 模型、普通聊天、Health Skill 或健康 Plugin 处理之前停止；不得读取或写入健康档案，也不得以普通聊天继续处理，从而避免非主人通过普通路径绕过主人准入。

### 2026-08-16 — Grilling Round 5

主人接受不泄露信息的拒绝表现：未授权私聊只收到“此身份未获授权，消息未处理”一类通用提示，不透露健康能力、健康档案是否存在或主人是谁；群聊保持静默，不回复，也不保存消息正文。

### 2026-08-16 — Grilling Round 6

主人确认按来源消息标识判断重复：两条正文完全相同但微信消息标识不同的消息，仍是两条独立来源消息，必须分别保留边界并分别处理；只有接口再次交付同一个微信消息标识时，才视为同一条消息的重复送达并只处理一次。不得再以发送者与正文内容的相同或相似作为去重依据。

### 2026-08-17 — CAN Research 后恢复 Grilling

当前事实排除“内置 Adapter 后再用 Hook 拦截”，因为此时逐条来源已经可能被去重或合批丢失；直接修改 Hermes core 虽可实现，却形成核心分叉。Hermes 正式 Plugin API 支持注册同名 `weixin` Platform Adapter 并优先于内置 Adapter，因此当前根路线是由同一健康 Plugin 在原始 iLink 消息进入时接管。若 Plugin 未注册，Hermes 仍可能回退内置 Adapter，所以“未证明健康 Adapter 覆盖已生效就拒绝启动、运行中绝不静默回退、Hermes 升级前重新验证 Adapter 合同”必须与该路线一并决定。

本轮还需决定两项无法由接口事实替主人选择的行为：第一，无法区分微信重投与主人有意再次发送时，是丢弃、重复处理，还是保留两次来源但暂停第二次健康效果并请主人消歧；第二，处理中断后若无法证明健康画像是否已经更新，是猜测成功/失败，还是公开标记“处理结果无法确认”并由主人决定是否重试。回复真实到达与主动发送重试的路线继续由[选择每日复盘、主动发送、恢复与运行状态路线](51-choose-daily-review-delivery-recovery-and-status-route.md)承载，本票只继承“接口未报错不等于主人已看到”的 CAN 事实。

### 2026-08-17 — Grilling Round 8 answer

主人确认批次接管合同：健康 Adapter 收到一批 iLink 消息后，先为每次接口投递形成独立 Hermes 接收时间并完成最小准入分类，不得先去重、合批、调用模型、修改健康画像或发送回复。只有该批每次投递的持久接收登记与腾讯返回的新同步游标在同一次本地提交中全部成功后，后续轮询才使用新游标；任一登记或游标写入失败时保留旧游标，本批不产生健康画像、任务、诊断或回复等业务效果。游标推进只表示 Hermes 已可靠接管该批投递，不表示健康处理已经完成。

主人同时确认按授权阶段限制持久内容：未授权私聊、群聊及身份或私聊属性不明确的投递只保留不含正文、媒体或健康内容的最小拒绝/异常登记；待绑定身份只保留完成初始化与知情同意所必需的证据，不创建或更新健康画像；只有已经激活的授权主人投递才可关联受保护的临时处理内容与逐次来源。具体数据结构、加密、保留、清除和删除覆盖由下游健康画像与保护路线决定，接收登记不得成为第二份健康画像或完整聊天历史。

## Answer

微信首发采用同一个 Partner Hermes 内、由同一健康 Plugin 注册的同名 `weixin` Platform Adapter 覆盖路线。该 Adapter 在内置微信正文去重、快速文本合批、普通模型处理和任何画像更新、任务变化、诊断结果或回复之前接住原始 iLink 投递；可以复用 Hermes 现有连接与发送能力，但不得先经过会丢失逐条来源的内置入站处理，也不修改 Hermes core、不新增 Agent、sidecar 或 LLM Gateway。

同一健康能力包还提供普通、可发现的 Health Skill：其名称与简短说明进入 Hermes 的技能索引，由同一个 Hermes 在相关时按需加载完整流程说明；健康 Plugin 暴露的 Tool 也可由 Hermes 按需发现和调用。模型可以决定是否展开或调用具体健康能力，但不能决定是否执行 Adapter 的身份、逐次来源和失败关闭保护。仅注册为不进入普通技能索引的 Plugin Skill 不满足自主发现要求；七个产品能力入口最终怎样映射为 Skill、Tool、Command 或自动流程，留给[选择健康能力入口与 Skill/Tool 契约](55-choose-health-capability-entrypoints-and-skill-tool-contract.md)。

该覆盖是上线不变量：启动前必须证明健康 Plugin 已启用、`weixin` 实际解析到健康 Adapter，且目标 Hermes 版本满足已经核验的 Adapter 合同；任何一项无法证明就拒绝启动。运行中接入、来源、授权或保护异常时失败关闭，不得静默回退到内置 Adapter 或普通聊天；Hermes 升级前必须重新通过同一合同验证。具体启动探针、版本声明和合同测试留给 Spec 与实施票。

首次绑定采用“预先指定、主人本人接受”：上线者只指定一个真实主人微信私聊身份为待绑定身份；技术白名单、最先发消息或操作者指定都不等于已经授权。该身份本人完成知情启用和恢复准备后才成为唯一活动主人。未授权私聊在正文进入模型或任何聊天处理前停止，只可得到不泄露健康能力、画像是否存在或主人身份的通用拒绝；群聊静默。两者均不得读写健康画像或保存正文；身份或私聊属性无法确认时同样失败关闭，且不向无法确认的目标回复。

Adapter 对每次 iLink 投递分别保留实际可得的接口、发送身份、上游标识与协议时间、字段缺失情况及独立 Hermes 接收时间；不得伪造缺失字段，也不得把正文相同、时间接近、标识相同或不同单独当作主人意图或恰好一次保证。Round 6 中“不同标识必定是两次主人动作、相同标识必定是重投”的推断明确撤回。

一批 iLink 投递只有在“每次投递的持久接收登记/处置状态 + 新同步游标”于同一次本地提交中全部成功后才推进游标；提交失败时保留旧游标，且本批不产生健康画像、任务、诊断或回复等业务效果。游标只证明 Hermes 已可靠接管投递，不证明健康处理完成；保留旧游标也不冒充腾讯服务端已经保证重投，失败后的实际重取行为仍须在获准的真实微信实验中验证。接收登记必须能够区分尚待处理、处理中、已完成、明确失败和结果无法确认等事实，但具体状态名与数据结构留给 Spec。

持久内容按授权阶段分层：未授权私聊、群聊及身份/私聊属性不明的投递只保留不含正文、媒体或健康内容的最小拒绝/异常事实；待绑定身份只保存初始化、本人接受与知情同意所需证据，不创建或更新健康画像；只有已激活主人投递才可关联受保护的临时处理内容及逐次来源。接收登记只是接管与恢复依据，不得成为第二份健康画像或完整聊天历史；其介质、加密、保留、临时内容清除和永久删除覆盖由[选择单一健康画像、主人权利与保护路线](49-choose-health-record-rights-and-protection-route.md)决定。

当现有来源不能区分接口重投与主人有意再次发送时，两次投递均保留，不凭正文或标识静默丢弃，也不自动产生第二次画像更新、任务变化、诊断结果或重复回复。只有该歧义会改变健康判断或下一步时，才由同一个 Hermes 向主人确认一次；未确认前保持未决，危险检查与危险升级不得等待消歧。

处理中断后，能够证明最终健康处理结果已经提交时不重做，能够证明尚未提交时恢复原操作；若无法证明健康画像是否已经更新，则明确标记并向主人显示“处理结果无法确认”，既不声称成功，也不声称没有记录，且不自动重试，由主人决定是否重试。只有明确判定为非健康的已授权消息才可保持原消息边界交给同一 Hermes 的普通聊天；健康、混合或无法确定的消息始终留在健康路径并继承失败关闭边界。

本票只决定微信入站接管、身份准入、逐次来源、接管提交和入站恢复语义。健康画像及数据权利由 Ticket 49 承载，诊断知识与安全强制由 Ticket 50 承载，主动发送、主人真实到达、每日复盘、投递恢复和运行状态由 Ticket 51 承载；接口未报告错误仍不得冒充主人已经看到回复。
