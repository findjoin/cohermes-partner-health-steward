# 20 — 通过微信完成主人控制、查看者授权和私密查看

**What to build:** 让画像主人通过自然微信表达完成自查、单一查看者授权与撤回、主动触达暂停与恢复、健康记录停止与恢复；完整健康查看由 sidecar 直接发送，不进入普通聊天模型或会话历史。

**Blocked by:** 16 — 让一条已同意的健康微信消息可信入档；17 — 建立严格幂等的微信健康投递；18 — 完善自动判别与停止记录生命周期

**Status:** resolved

- [x] partner-only 插件提供主人自查、查看者 grant/revoke、暂停/恢复主动触达和停止/恢复健康记录的自然语言可选工具，无需 slash 前缀。
- [x] 每个控制动作使用当前已认证消息签发的一次性收据，并绑定 action、sender、message ID、UTC 时间以及查看者目标或暂停截止时间；重放和篡改失败关闭。
- [x] 第一版只允许一个预配置查看者 sender ID；服务器管理员身份不自动获得查看权，也不能把授权改给其他联系人。
- [x] 主人始终可以自查；查看者只有在有效 grant 后可只读查看，revoke 后立即阻止未来查看和周报。
- [x] 完整视图由 sidecar 结构化生成并通过幂等微信通道直接发送，不进入普通聊天 LLM、普通 Hermes 会话历史或 memory 投影。
- [x] 只有主人或当前获授权查看者在当前轮明确要求模型分析时，所需最小范围才可交给已批准健康模型；普通查看不自动调用模型。
- [x] 主动触达暂停和健康记录停止保持为两个不同状态，并按各自规则影响任务、判别、被动回答和恢复。
- [x] 主验收覆盖主人、查看者、管理员、撤权、参数篡改、收据重放和普通会话历史隔离，并观察微信结果、授权查询及无内容审计。

## Comments

- 2026-08-09：用户显式调用 `$implement Ticket 20`。自然语言控制落在 production partner 微信适配器的认证后、普通文本合批前 handler；它使用原始 sender、message ID 和 UTC 签发动作绑定收据。完整查看和明确分析均由该私密控制面直接回复微信，不进入普通 Hermes 工具结果、会话历史或 memory 投影。
- 2026-08-09：记录停止/恢复与健康消息 preflight 共用到达顺序门，但完整查看、固定健康模型分析和微信网络发送不占用判别预算。停止/恢复结果由到达序列单消费者投递，保证最终记录状态与用户看到的微信结果顺序一致。

## Answer

Ticket 20 已于 2026-08-09 完成本地实现。partner-only 插件现在识别无 slash 的明确自然语言控制，拒绝否定、疑问、复合动作及不受支持的暂停时长；每个动作只使用当前已认证微信轮次签发的一次性收据。sidecar 与插件共同强制唯一预配置查看者，管理员和任意联系人不继承查看权；撤权后交互查看、明确模型分析和未来周报均失败关闭。主人在尚无首条健康事实时也能获得结构化空视图。

完整视图通过有界 sidecar 流和可重组微信分片直接幂等发送；部分分片失败不会在重放时误报完整。普通查看不调用模型，只有主人或当前授权查看者的当轮明确请求才把有界紧凑画像交给固定健康模型。主动触达暂停与健康记录停止仍是独立状态；记录停止/恢复既与后到健康判别线性化，也保证连续控制的微信回执不逆序。

验证证据：`python -m unittest discover -s ops\partner-health-steward\tests` 共运行 464 项，441 项通过、23 项按当前 Windows Python 缺少 AF_UNIX 或 Linux peer credentials 的条件跳过；`python -m compileall -q ops\partner-health-steward` 与 `git diff --cached --check` 通过。本仓库没有配置或安装 Python 类型检查器，因此语法检查不冒充类型检查。本票不宣称真实 partner Linux、微信或部署验收；这些仍归 Ticket 14/15。

两轴固定点复审无剩余 P1。保留一项非阻塞崩溃一致性边界：收据已持久消费后、业务提交或首次 delivery ledger 建立前若进程退出，该认证轮不能原样恢复；相同 message ID 继续失败关闭，用户需发送新的已认证明确指令重试。该窗口不会放宽授权、重放旧指令或产生伪成功标记。
