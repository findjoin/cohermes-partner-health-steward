# 完整健康管家当前能力与约束报告

调查日期：2026-08-20

## Answer

### 结论

当前 CAN 可以闭合，并进入 HOW 技术路线选择。

现有证据已经给出至少一类与最终 TO 相容、受现实承载能力支持、没有被一手证据证明不可行的实现路线族：在同一个 Partner Hermes 中，由健康 Plugin 拥有健康入口后的受管执行边界，连接一套单一权威健康状态、任务与投递运行框架、受约束的模型调用边界，以及版本化且须经授权和医学审核的诊断内容链。这里确认的是“存在可实施空间及其硬约束”，不是选择数据库、接口、规则引擎、医学来源、模型或具体 Plugin 内部结构。

当前正式 Partner 尚未部署健康 Plugin，也尚未形成画像、证据、任务、诊断范围、运行状态和真实主人健康结果。这些是 HOW 之后的实现、外部前提和验收工作，不再被错误解释成 CAN 不可行。

本轮没有发现仍会决定“HOW 是否存在”的 CAN fog，也不需要继续换病种重复调查。已发现的确定性反例排除的是若干朴素或旧候选路线，不是排除全部可实施路线。

### 证据层级与本报告能证明什么

本报告只合并已有调查结果，没有向正式微信发送消息、调用真实健康模型、写入正式健康资料、改变服务或执行破坏性实验。

| 证据层级 | 本轮用途 | 不能冒充的结果 |
|---|---|---|
| 官方与上游合同 | 判断 Hermes、iLink、医学来源和许可入口对外声明了什么 | 目标现场已经按该合同部署 |
| 固定源码 | 判断确定版本中的扩展面、失败行为、持久化和投递语义 | 当前脏工作树与目标运行字节完全相同 |
| 目标现场只读核验 | 判断 2026-08-20 的版本、配置、进程、入口、Plugin、Skill、Cron 和依赖事实 | 健康产品能力已经实现或通过验收 |
| 工作树候选与本地测试 | 证明局部原语可以运行，并暴露确定性冲突 | 候选已部署，或旧测试合同满足现行 TO |
| 获准实验 | 留给实现后的真实模型、微信、故障、删除、恢复和迁移验收 | 本轮已经完成真实主人产品验收 |

阶段解释以[修正未实现系统的能力判定、诊断范围门禁与负向研究计数](../issues/97-correct-can-preimplementation-feasibility-and-diagnostic-scope-gate.md)为当前权威：TO 保留最终硬门槛；CAN 只确认可实施性事实、限制、外部前提与未来验证义务；HOW 选择具体路线；实现后才取得实际许可、完成医学审核、激活范围并做真实主人验收。

### C01—C17 能力与约束闭合矩阵

#### C01 当前基线、Plugin 生命周期与可信执行

- 已证明：当前 Partner 的版本、提交、脏差异、服务、权限、入口、Plugin、Skill、Cron 和依赖可以枚举；Hermes 提供进程内 Tool、Hook、Middleware、Platform、Skill 和辅助任务扩展面；守约的纯进程内代码会随 Gateway 进程停止。
- 已排除：把普通 Plugin 加载、`register()`、Hook、Middleware 或 `pre_gateway_dispatch` 当作天然失败关闭的健康门禁。它们存在失败后基础 Hermes 继续、部分注册不回滚、无统一卸载和 teardown 的确定性路径。当前服务以 root 运行且缺少主要 sandbox，也不能冒充最小权限隔离。
- 交给 HOW：选择健康 Plugin 的完整加载判定、可信前提丢失后的失败关闭、全部进程内外副作用的生命周期、制品固定、权限与日志隔离、版本和状态迁移边界。
- 后续验证：部分加载、重启、停止、外部副作用、权限、日志和资产导出恢复实验。

依据：[当前 Partner Hermes 基线、Plugin 生命周期与可信执行边界](19-current-partner-hermes-baseline-plugin-lifecycle-trust-20260820.md)。

#### C02 能力入口、初始化门禁与真实结果

- 已证明：Skill、Plugin Skill、Tool、Command、Platform Adapter、自然语言、内部 dispatch 和 Cron 都是可组合入口；Plugin Platform 可以承载后续专用接入。
- 已排除：用单独 Skill、模型是否选择 Tool、普通 Command、通用 Hook 或单个入口判断来证明“初始化前健康系统完全不启动”。旧候选只写入部分同意状态而未同时完成全部初始化对象，是部分结果冒充启用的反例。
- 交给 HOW：选择一份可查询、不可旁路、全有或全无的初始化权威；所有健康入口和内部流程都读取同一门禁；分别记录注册、可发现、开始调用、业务提交、返回、发送尝试、接口接受和主人实际看到。
- 后续验证：逐步中断初始化、重启、不倒填旧消息、模型不调用 Tool、直接 Command/dispatch、Cron 和另一 Plugin 等旁路，以及提交边界前中后的故障注入。

依据：[健康能力入口、初始化门禁与真实结果返回](20-health-capability-entry-initialization-gate-result-contract-20260820.md)。

#### C03 唯一微信准入、来源、重投与交付

- 已证明：当前微信配置为单值私聊 allow-list、全开放关闭、群策略关闭；固定 Hermes 提供渠道策略和 Plugin Adapter 覆盖面。
- 已排除：直接沿用内置微信事件链来保证逐次来源完整。该路径在准入前读取正文并形成短期正文指纹，先推进 cursor，再做正文去重和快速合批；相同正文可能在业务事件前被吞，快速消息只保留第一条来源。Telegram 仍启用，其他内部入口也存在。iLink 成功和本地 `client_id` 不证明主人看到。
- 交给 HOW：选择唯一健康入口的收敛与接管位置，在丢失逐条来源前形成受管接收事实；保留重复观察但冻结重复健康效果；健康接管失败不能回普通聊天；分开业务提交、回复形成、接口接受和主人到达。
- 后续验证：获准/未获准私聊、群聊、Telegram 和内部旁路，初始化前后，两次同正文、快速连发、断线重启、cursor 窗口、发送超时和主人端实际可见。

依据：[唯一微信准入、排他分流、逐次来源与重投结果](21-unique-weixin-admission-routing-provenance-replay-results-20260820.md)。

#### C04 受管状态、保护隔离与单一权威

- 已证明：目标提供 SQLite、标准密码学库、systemd credential、目录权限和 sandbox 等可选承载原语；工作树证明不可变版本、当前指针、局部共同修改、原子文件替换、受控临时导出等局部机制可以实现。
- 已排除：把普通 Session、FTS、Memory、日志、cache 或通用 backup 当作健康权威；直接继承旧 sidecar 的多文件、多库、明文投影、独立密钥、审计、source cache、delivery ledger 和不完整 restore。旧投影还会进入非 Cron 普通会话，是隔离反例。
- 交给 HOW：选择唯一受管状态权威及完整对象清单；建立稳定身份、引用完整性、候选/最终隔离、跨外部效果的可恢复状态与明确未知；闭合普通历史、Memory、日志、缓存、备份、导出和临时副本隔离。
- 后续验证：每个提交点前中后强停、并发撤权、磁盘满、权限拒绝、密钥损坏、备份恢复以及所有普通存储面的无健康正文扫描。

依据：[受管健康状态数据平面、保护隔离与单一权威](22-managed-health-state-plane-protection-and-single-authority-20260820.md)。

#### C05 六域画像与三类证据

- 已证明：工作树已有个人证据分型、不可变画像版本与当前指针、冲突降为待核实、资料卡版本替代和按 ID 链接等局部原语；现行六域、固定二级主题、顶部当前状态、三类证据和四职责写权语义已经明确。
- 已排除：直接复用旧“四类结论 + 三种个人证据 + 独立资料库”对象模型；把资料标签冒充六域；把搜索命中、任务完成或模型文本升级为个人事实；在未获主人同意时改变基础主题。
- 交给 HOW：选择六域与固定主题的稳定表示；空主题明确未知；每项证据只有一个权威卡并携带来源、时间、版本、准入、用途、不确定性、支持/反对/限定、纠正、撤回、失效和后继关系；画像和任务只引用；四职责只修改各自获准对象。
- 后续验证：空画像、主题变更批准、冲突、纠正、撤回、过期传播、悬空引用、重复卡和三类证据越级。

依据：[紧凑六域健康画像与三类证据卡](23-six-domain-portrait-and-three-class-evidence-capabilities-20260820.md)。

#### C06 开放健康任务与四项职责

- 已证明：工作树能表达有限任务条件、资料当前性、dispatch、跳过和接口结果；Hermes 提供内部任务与调度承载面。
- 已排除：直接复用旧封闭任务类型和状态集。它们不是 `active / solved / failed / cancelled`；外部结果未知会被吞成 `failed`；暂停主动支持或停止记录会批量取消任务，违反控制分离。
- 交给 HOW：选择一套任务权威，表达建档门槛、承担者、阶段、验收、四标签、范围批准、撤权、四职责写权限、独立未知事实、延期/调整/取消和终态后继。
- 后续验证：从自然消息到建档、合并、补证据、批准外部动作、结果未知、主人控制、终态和后继任务的完整旅程。

#### C07 每日复盘、通知与投递恢复

- 已证明：固定 Cron 与旧候选提供当地日计算、同日去重、任务执行状态、接口接受/拒绝/不确定和稳定防重键等原语。
- 已排除：把 Cron `completed`、任务 `sent` 或接口 accepted 当作业务复盘完成、主人到达或健康改善；把未知外部效果改成失败；用固定 04:00 小窗口和一次短重试冒充任意停机恢复后的当前态重判。
- 交给 HOW：选择自然日业务账本、无变化安静、最近复盘结论、五类普通通知选择、不可关闭关键通知、暂停/停止记录分离、未知冻结及恢复不补积压的统一路线。
- 后续验证：时区和日界、长时间停机、重启、在途断连、重复触发、未知决定和真实微信交付分层。

#### C08 首跳模型路线与主人派生查询隔离

- 已证明：当前磁盘配置能定位名义 provider、base URL、API mode 和 model；Hermes 有独立模型调用和扩展出站面；旧候选有固定 endpoint/model、no-tools 调用和局部漂移拒绝原语。
- 已排除：原生 `ctx.llm` 单独证明发送前实际首跳和全部 fallback；普通 Agent 直接承载健康调用；按主人消息关键词选择 URL 并在缓存缺失时向首跳路线外实时回源。后者是明确违反查询来源合同的工作树反例。
- 交给 HOW：选择可在发送前绑定“主人同意的首跳—实际首跳”的强制面；统一约束 Tool、搜索、缓存回源、MCP 和普通 Agent；首跳变化暂停需要新路线的健康处理，同时不封死无需新接收方的数据权利。
- 后续验证：endpoint/provider/API mode/model/fallback 变化、网络出口、缓存 hit/miss 和本地权利继续。

依据：[首跳模型路线、主人派生查询隔离与非诊断问答](24-first-hop-model-route-owner-derived-query-isolation-nondiagnostic-answer-results-20260820.md)。

#### C09 医学内容治理与范围候选形成

- 已证明：一手来源可以形成明确、版本化、可审计的窄范围候选；BMI 调查已定位国家卫健委中文来源、版本及需要联系权利人确认的复用边界，高血压调查还定位了 NICE 的国际/AI 许可入口及中国来源的权利不确定性；两者均未取得实际生产许可。两项调查也明确了医学审核应覆盖的内容、诊断规则和危险边界。
- 已排除：公开可读即等于可供 AI 产品生产复用；模型参数知识、搜索摘要、术语库、患者科普或药品接口单独充当诊断规则；未经授权和审核自行拼接中国与 NICE 等来源。
- 交给 HOW：选择具体首发范围候选、来源与版本组合、许可取得路径、更新/撤回治理和合格医学审核流程。
- 外部硬前提：实际取得所需权利，冻结中文版本清单，取得合格医学专业人员对实际内容、诊断规则和危险边界的审核结果。未完成前范围不得激活。

#### C10 明确诊断范围专属准入

- 已证明：候选范围可以精确描述适用人群、必要资料、允许输出、排除边界、危险优先、来源版本、失效条件和可观察验收；BMI 与高血压提供了不同证据几何的实例。
- 已排除：以病种名字、单个阈值、公开指南或模型一次回答冒充可激活范围；以当前范围为零反推 CAN 不可行；为了凑轮次不断更换病种。
- 交给 HOW：从已有候选及其真实权利/审核可达性中选择首发范围路线，定义范围注册、准入、失效退出和范围级验收方法。
- 外部硬前提：实际许可、医学审核和范围产品验收通过后才可激活；完整首发最终至少一个范围实际激活。

#### C11 诊断资料、容量与结构化终态

- 已证明：Hermes 可承载受限模型调用、本地结构校验和受管资料装配；“最小但完整”的资料角色、支持/反对证据、关键未知、容量证明及最终提交边界已经可判定。
- 已排除：旧候选静默 `cards[:8]`、自由正文、静态窗口数、粗略 token 估算、事后 usage 或 `stop` 作为完整性证明；当前固定适配器会丢失 `incomplete / failed / incomplete_details` 等终态，不能原样用于最终诊断。
- 交给 HOW：选择保守输入预算、必要资料完整性证明、输出预留、结构化响应、权威终态与实际 model/fallback 证明、未通过候选隔离以及最终写入/发送边界。
- 后续验证：边界大小、中文、附件、结构化输出、截断、半流、适配器失败、fallback 和提交前后故障。

#### C12 范围隔离与安全五分支

- 已证明：最终 TO 已明确范围内、范围外、危险升级、危险未明和安全能力不可用五类结果及其最小留存；Plugin 扩展面允许建立受管确定性检查和唯一放行路径。
- 已排除：关键词未命中即安全；提示词、免责声明、Skill、模型自律、普通 Tool、通用 fail-open Hook/Middleware 充当不可绕过医疗安全闸门；范围外输出残缺疾病排序；把危险未明或安全能力不可用写成低风险。
- 交给 HOW：选择健康 Plugin 私有路径内不可绕过的范围准入、安全条件、处方药禁令、失败关闭和确定性结果收敛；明确每个分支的记录和发送行为。
- 后续验证：范围内外、来源特异危险组合、关键事实缺失、安全组件故障、旁路、重投、调药同义改写和输出对抗。

#### C13 诊断修订链与当前判断

- 已证明：不可变版本、当前指针、来源卡后继和投递恢复等底层原语存在；修订、降级、撤回、替代、依据失效、主人纠正与异议、权威未知的产品语义已经明确。
- 已排除：把普通画像 `current_version_id` 或资料卡 `superseded_by` 冒充完整诊断修订链；模型重跑自动改判；医生结论自动覆盖 AI 判断；接口接受冒充纠错已经到达主人。
- 交给 HOW：选择诊断专属稳定身份、前驱后继、适用期、变更原因、依赖传播、单一当前或明确无当前、部分提交恢复、权威未知隔离和一次必要纠错通知的统一路线。
- 后续验证：个人证据纠正/撤回、知识与安全规则失效、医生结论冲突、并发改判、崩溃和纠错发送未知。

依据：[明确诊断范围候选形成、准入与诊断全链](25-named-diagnostic-scope-governance-and-full-chain-capabilities-20260820.md)、[成人疑似原发性高血压测量确认与分流链](27-adult-hypertension-measurement-confirmation-and-urgent-referral-chain-20260820.md)。两份报告中的“尚未实现或未激活即 CAN 失败”旧阶段判断已被后继修正，医学事实、源码限制和确定性反例继续有效。

#### C14 主人权利、分离控制、删除和防复活

- 已证明：工作树有查看、导出、暂停/恢复主动联系、停止/恢复记录、局部删除、key 销毁、投影清理和未知投递冻结等原语。
- 可实施性依据：历史 CAN 已证明两类可进入 HOW 比较的域外最小代际原语——带事务或 CAS 的强一致 KV，以及带 generation 条件替换的强一致对象 `current-head`。它们在业务单调校验、transition ID、未知回查和最小权限成立时，可以表达“旧本地或 VM 快照不得重新成为当前删除/撤权代际”；这只是候选能力，不是当前已接入的服务。
- 已排除：直接继承旧控制与删除合同。暂停和停止记录会错误取消任务；删除额外引入 10 分钟确认窗、固定 30 天备份期和“永久删除完成”通知；现有清单不覆盖全部副本，旧 Plugin、备份或 VM 恢复仍可能复活旧状态。
- 交给 HOW：选择完整数据与副本清单、相互独立的控制语义、删除代际和信任边界内防复活路线；若选择域外最小代际原语，必须同时选择实际资源、账号/地域、权限、费用、故障回查和本地失联时的失败关闭；不承诺删除主人已下载或站外持有的副本。
- 外部前提与 No-Go：当前没有已配置的域外强一致资源、凭据或 canary；在实际资源、最小权限、单调业务检查和 old-snapshot prototype 通过前，不得宣称防复活成立，也不得用本地 SQLite、加密、WORM 文档或 VM 内 tombstone 单独替代。
- 后续验证：查看、纠正、导出、停止记录、暂停支持、取消、撤权和删除的对照旅程；旧备份、旧 Plugin 和完整旧 VM 恢复；域外代际的 CAS 冲突、超时与未知回查；删除后只允许空白初始化。

可行性依据来自历史[【CAN】核验域外身份代际权威候选的强一致与防回滚能力](../issues/71-verify-external-owner-generation-authority-candidates.md)及其[强一致与防回滚能力证据](18-external-owner-generation-authority-candidates-20260818.md)。原身份迁移目标已经取消；本报告只重新判定其中可支撑删除、撤权和终态防复活的通用原语，不恢复旧身份路线。

#### C15 三态业务观测与故障隔离

- 已证明：旧候选能观察部分审计、复盘和 dispatcher 心跳，并持久化 firing/recovered；Hermes 与目标主机提供服务观测和外部 sink 承载面。
- 已排除：Gateway、systemd、Ticker、Cron 或单个 reader 存活即代表健康管家“活跃”。旧测试允许 `production_acceptance=blocked` 时仍报告 service healthy，也不会传播入口、画像、任务、控制、模型、安全、问答和诊断范围状态。
- 交给 HOW：选择跨故障域的业务状态聚合和隔离规则，形成主人可查询的活跃/异常/无法确认、最近确认时间、受影响能力、当前可依赖结果及一次转态通知。
- 后续验证：每个业务域的故障、最后一个诊断范围失效、可信入口前提丢失、观察者自身故障和恢复通知。

#### C16 权威资产完整迁移

- 已证明：工作树有发布文件 allow-list、hash manifest、staging、拒绝路径逃逸、加密主状态备份校验、恢复失败回滚和重复服务拒绝等局部原语。
- 已排除：只复制文档和 Skill、只复制 profile、只替换主状态 blob 或只校验文件哈希就声称同一健康管家已完整迁移。现有 manifest 不覆盖全部权威文档、Skill、画像、证据、任务、批准、控制、未知、交付、删除状态、多个 ledger/cache 和密钥，也没有源端冻结与目标单一接管。
- 交给 HOW：选择完整语义资产清单、版本兼容、快照代际、源端停止、目标接管、单一写入权威、失败关闭及迁移暂存的删除覆盖。
- 后续验证：可丢弃源—目标迁移、缺项、错误权限、密钥缺失、版本不兼容、中断、旧端重启和引用完整性。

#### C17 有依据的非诊断健康问答

- 已证明：旧候选有不读普通历史的单轮 no-tools 调用、有限画像摘要和来源卡、当前卡 ID 白名单、无正文投递 ledger 等局部原语。
- 已排除：直接继承只有 `answer_text + source_card_ids` 的自由正文结果；该结构不能强制区分个人事实和一般知识，也不能证明资料类型、来源、时间、用途、不确定性、关键未知和安全下一步。疾病排序、诊断标签、排除结论或个体化调药也没有确定性效果门禁。
- 交给 HOW：选择结构化非诊断结果、资料最小选择、诊断效果交接、安全优先、画像更新独立结果，以及结果形成、业务提交、发送尝试、接口接受和主人到达的分层权威。
- 后续验证：夜班与睡眠、测量含义、个人事实与一般知识冲突、诊断效果越界、危险三状态、来源失效、模型输出对抗及真实主人微信交付。

依据：[首跳模型路线、主人派生查询隔离与非诊断问答](24-first-hop-model-route-owner-derived-query-isolation-nondiagnostic-answer-results-20260820.md)。

任务、控制、状态和迁移节点的综合依据：[健康任务与受管运行框架旅程](26-health-task-managed-runtime-state-journey-capabilities-20260820.md)。

### 已排除的路线，不得在 HOW 中重新包装

1. 单靠 Skill、提示词、模型自律、普通 Tool、通用 Hook/Middleware 或 `pre_gateway_dispatch` 承担初始化、身份、医学安全或失败关闭。
2. 让普通 Agent、Session、FTS、Memory、日志或通用 backup 成为健康权威或健康正文的默认通道。
3. 原样使用内置微信正文去重和合批链，同时声称逐次来源完整、exactly-once 或主人已收到。
4. 原样复用旧 sidecar 的对象模型、明文投影、自制密码学、多提交面和不完整 restore。
5. 原样复用旧任务、暂停、停止记录、删除、监控和迁移合同。
6. 使用主人消息决定首跳路线外的实时搜索、URL 回源或缓存补取。
7. 把公开可读医学内容、模型常识、搜索摘要或未审核来源直接升级为诊断规则。
8. 使用自由正文、静默卡片裁剪、静态窗口数或丢失终态的适配器形成最终诊断。
9. 用关键词、免责声明、提示词或 fail-open 扩展点充当医疗安全强制层。
10. 用普通画像版本、资料卡替代或模型重跑冒充诊断修订权威。
11. 用接口 accepted、任务 sent 或 Cron completed 冒充主人到达、健康改善或业务验收完成。
12. 因为产品尚未实现、许可尚未获批、审核尚未签字或范围尚未激活，就重新宣布 CAN 不可行并继续换病种调查。

### 足以进入 HOW 的路线空间

以下是由 TO 与现实承载能力共同限定的路线空间，不是本报告选择的最终方案：

1. **执行与入口层**：同一个 Partner Hermes 中的健康 Plugin 使用受支持扩展面接管健康入口后的全部受管处理；初始化、自然语言、显式能力、任务与自动流程共享同一权威门禁，关键约束不依赖 fail-open 通用回调。
2. **单一权威状态层**：一套受管对象关系拥有画像、三类证据、任务、批准、控制、诊断修订、未知、交付和历史；普通 Hermes 历史与 Memory 不成为第二权威；无法与外部效果原子提交时显式进入未知。
3. **任务与运行层**：开放健康任务框架负责建档、阶段、验收和四标签；四项职责只返回候选或受权结果；自然日复盘、通知、投递恢复和三态观测共享同一任务与状态事实。
4. **模型与查询层**：健康资料只进入主人已同意且可在发送前证明的首跳路线；主人派生查询不出该路线；非诊断问答和诊断候选都有结构化结果及发送前效果边界。
5. **诊断内容与安全层**：对以后选定的一项明确窄范围，采用受权利、中文版本、更新退出和医学审核治理的内容；在健康 Plugin 私有路径内完成范围准入、最小且完整资料、容量和终态证明、五分支安全收敛、最终提交与诊断修订链。
6. **权利、观测与迁移层**：主人控制、永久删除、防复活、业务三态和完整迁移都作用于同一权威对象清单及其全部受管副本。

每一层都有已证明的承载原语，也都有至少一种没有被现有一手证据排除的实现方式；具体组件、职责分配、事务边界、许可来源、规则结构、进程布局、加密与密钥、投递、监控、迁移和验证工具必须由 HOW 统一选择。

### 仍未发生但已经归位的硬门槛

这些事项没有被“忽略”，而是已经放回正确阶段：

- 取得首发诊断内容的实际使用权、翻译或规则化权利；
- 冻结并维护中文来源与版本清单；
- 取得合格医学专业人员对实际内容、诊断规则和危险边界的审核结果；
- 实现并部署健康 Plugin、单一权威状态和全部任务/安全/权利能力；
- 完成模型路线、容量终态、查询出口、医学安全、崩溃恢复、删除防复活、三态观测和迁移实验；
- 通过真实主人、真实微信的入站、问答、任务、主动投递、重复/未知和状态通知验收；
- 至少一个明确诊断范围通过全部门槛并实际激活。

任何一项未通过时，相应范围或完整首发仍必须失败关闭；CAN 闭合不会降低这些 No-Go。

### 仍需 HOW 选择、但不再属于 CAN fog 的问题

- 健康 Plugin 内各职责、入口、门禁与状态边界如何组合；
- 受管对象、事务、日志隔离、密钥、备份和删除防复活采用什么具体路线；
- 微信入口在内置去重/合批前后如何接管，其他入口如何隔离；
- 首跳路线如何证明、变化如何冻结、所有出站能力如何统一约束；
- 首发诊断候选、来源、许可、中文版本和医学审核流程如何选择；
- 容量、结构终态、安全五分支、诊断修订和非诊断问答使用什么确定性结构；
- 任务、自然日复盘、投递未知、通知、三态观测和迁移如何形成一个可验收运行框架；
- 实现后分层验证采用哪些 canary、故障注入、恢复和真实主人验收方法。

这些问题会改变“怎么做”，但现有事实已经足够约束选择，不再需要新的 CAN 调查才能开始。

### 完整 TO 覆盖判断

[完整首发健康管家的产品合同与成功条件](../issues/75-close-first-release-health-steward-product-contract.md)中的八段主人旅程、失败结果、权利、不变量和完整首发门槛，已经通过[完整 TO 能力链与追溯关系](../issues/76-rebuild-complete-to-capability-chain-and-traceability.md)映射到 C01—C17，并由本报告逐项闭合到当前能力事实、确定性限制、HOW 选择项、外部前提和未来验证义务。

因此：

- 没有未覆盖的 TO 节点；
- 没有互相冲突的现行 CAN 结论；
- 没有仍会决定 HOW 是否存在、但尚未调查的能力未知；
- 没有一手证据证明所有可实施路线都被排除；
- BMI 与高血压调查不计负向可行性轮次，当前累计负向轮次为 0；
- CAN 阶段可以结束，下一阶段应选择一条统一 HOW 技术路线；
- 在 HOW、实现、外部前提和真实产品验收完成前，不得声称健康管家已经可用、稳定、完整首发或有已激活诊断范围。

本报告不承诺总体法律或监管合规，不建立医生工作流、多主人、多入口、现实身份核验或抵抗恶意最高权限主体的能力，也不选择最终实现路线。
