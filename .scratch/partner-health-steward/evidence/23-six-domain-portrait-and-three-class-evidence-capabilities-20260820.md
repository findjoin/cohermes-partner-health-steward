## Answer

截至 **2026-08-20 16:08（Asia/Shanghai）**，当前 Partner **没有已部署、可定位的能力**能够表达并核验现行 TO 的“顶部当前状态 + 六个固定一级领域 + 固定基础二级主题 + 三类不可互换证据卡”。前置 C04 同日现场只发现一般 Python/SQLite/密码学/systemd 原语，Partner profile 的健康 Plugin manifest 为零，仓库 sidecar 及其状态也未部署；因此不能在真实 Partner 上做六域状态前后差异、主题批准、冲突/撤回或引用唯一性验收。[L1]

Hermes v0.20.0 固定 Plugin 表面允许 Plugin 注册带 JSON schema 的 Tool 并由 handler 执行业务逻辑，所以 Hermes 本身没有阻止以后暴露结构化画像/证据职责接口；但 `PluginContext` 不提供现成的健康对象模型、受管 Plugin 状态、迁移或跨对象引用合同。它只证明“以后可以接入具体实现”，不证明六域或三类证据已经存在。[F1][L1]

当前工作树旧 sidecar 是**未部署、dirty/untracked 的候选**。它证明了少量可复用的 CAN 原语：个人陈述、测量和主人转述医生内容可分型准入；一次修改能同时产生个人证据、不可变画像版本和唯一 `current_version_id`；高影响冲突可以降为“待核实”且禁止自动派生任务；通用资料卡会保持 `untrusted_data`，查询结果不会直接返回个人事实或任务动作；任务候选可以只保存证据 ID 而不保存消息正文。[W1][W2][W3][T1][T2][T3]

但这个候选的现行对象仍是四类旧结论 `state / habit_goal / interaction_preference / task_context` 和一段全局摘要；通用资料库的所谓“六个固定标签”其实是 `topic / symptom_behavior / target_population / evidence_type / region_language / freshness` 六种资料元数据，不是六个健康画像领域。个人证据的三种 `evidence_kind` 也只是**个人健康证据内部的来源子型**，不是“个人健康证据 / 通用权威知识 / 任务过程证据”三个一级类型；任务过程只散落在 task/audit 中，没有任务过程证据卡。[W1][W2][W3]

候选还没有固定二级主题拓扑、主题变更的主人批准记录、每个主题的明确未知、统一证据卡生命周期、支持/反对/限定关系、个人证据纠正/撤回接口、跨三类证据的唯一引用完整性或任务过程证据准入。源码中部分对象有 ID、版本、`current/superseded_by` 或字符串引用，但这些局部机制不能证明“每条证据只有一张权威卡，画像和任务只链接且引用必然有效”。[W1][W2][W4]

因此 C05 的结论是：**底层原语部分可用，完整产品语义在当前正式 Partner 中未实现，在当前仓库候选中也未实现。** 这项负向 CAN 已把“能复用什么、缺什么、如何复现实证”调查清楚，可以作为完整 CAN 报告的输入；它不降低 TO，也不选择文件、字段、数据库、索引介质、四个 Skill、Plugin/sidecar 组织或任何技术路线。只有全部 CAN 票与能力闭合票完成后，HOW 才能依据这些事实选择路线。[P1][P2][L1]

## 3. 当前正式 Partner 与固定 Hermes 能证明什么

前置 C04 已证明正式 Partner 没有健康 Plugin manifest，也没有部署本仓库 sidecar、健康状态、密钥、备份、投影或导出目录；普通 Hermes Session/Memory/FTS/log/cache/backup 又不是健康权威。[L1] 所以当前 LIVE 结论不是“六域做得不够好”，而是**没有可验收的六域实现对象**。

固定 Hermes 的 `PluginContext.register_tool(name, toolset, schema, handler, ...)` 可以注册结构化 Tool，JSON schema 可约束一次调用输入，handler 可以转交具体业务能力。[F1] 但 schema 不能单独保证：

1. 六域和固定二级主题跨多轮仍是同一当前拓扑；
2. 主题变更已获得主人批准；
3. 三类证据不可互换；
4. 证据纠正、撤回或失效会传播到画像理解；
5. 画像、任务与证据引用只指向一张当前可确认的权威卡。

这些都是具体状态和职责接口必须证明的业务不变量，不能由“Plugin 可注册 Tool”推出。

## 5. 四项职责接口与写权限

现行 TO 要求画像维护、证据维护、主人询问和文献查找各自只返回真实职责范围内的结果，询问与查找不能直接准入证据或改写画像；任务框架再依据这些结果推进任务。[P1]

当前候选没有这组可核验的角色/写权限合同：

| 职责 | 当前候选接口 | 写权限判断 |
| --- | --- | --- |
| 健康画像维护 | `health.profile.message.admit` 接受主人消息和模型候选，同一次修改直接追加个人证据、画像版本并切换当前画像。[W1][W4] | **过度耦合**：没有独立证明“证据已准入”后才允许画像维护写当前理解的职责结果 |
| 健康证据维护 | 个人证据准入嵌在画像修改中；通用 `SourceLibrary` 单独维护资料卡。[W1][W2] | **不完整**：没有统一三类证据准入、支持范围和纠正/撤回写权限 |
| 主人询问 | 没有独立的“只取得最小回答、返回候选个人证据”的职责结果；主人消息可沿上述 admit 路径直接进入画像修改。[W1][W4] | **无独立门禁** |
| 文献查找 | `health.source.query/scan` 与 `SourceLibrary` 只返回资料卡；模块明确不写画像结论或任务，测试也证明不生个人事实或动作。[W2][W4][T2] | **局部正确**：取得候选资料与个人事实分离，但没有后续证据维护准入和用途关系 |
| Plugin 任务框架 | 日常复盘路径既能刷新旧画像结论，又能建立旧任务候选。[W3] | **边界不同于 TO**：没有只消费四项职责结果的任务推进接口，也没有按职责限制写目标对象 |

固定 Hermes 只提供通用 Tool schema/handler 和进程内 Plugin 代码执行面，不替具体实现做角色鉴权或业务写权限隔离。[F1] 因此“以后可以注册四个接口”是可用原语，“当前四项职责已经对齐并被强制”则不成立；四个 Skill 如何实现仍不得在 CAN 中选择。

## 6. 用具体场景说明结论

### 场景 A：主人说“近期上夜班，所以每天只能睡四小时”

现行产品应把“睡眠不足”及主人报告的夜班关联放在“身体功能与主观身体体验 → 睡眠”，保留真实来源与不确定性，不建立“社会与环境背景”第七域。[P1][P2]

旧候选最多把它写成 `category=state`、任意 `dedupe_key=sleep` 和摘要文字；它既没有“身体功能与主观身体体验/睡眠”的结构化身份，也没有“主人陈述关联但未独立验证因果”的关系。文字看起来正确仍不能核验六域合同。[W1]

### 场景 B：初始化后从未谈过过敏史

现行产品的固定“过敏、不耐受与危险警示”主题应保持明确未知，而不是被模型补成“无过敏”。旧候选的空画像只是空 `conclusions` 和空 summary；没有固定主题清单，就无法区分“该主题按合同存在且未知”与“实现根本没有该主题”。[W1]

### 场景 C：主人先说“疼痛很重”，后来又说“完全不痛”

候选测试证明，若两条不同时间陈述带同一高影响冲突键，当前结论会降为 `unverified_hypothesis`，关闭自动任务资格，并标记已发出补问。这是有价值的未知处理原语。[W1][T1]

但它把当前结论压成“待核实”，没有把两张证据卡分别标为支持/反对/限定，也没有个人证据撤回或纠正链。因此它不能完成现行证据追溯合同。

### 场景 D：检索到一份 WHO 睡眠资料

候选资料库可以把内容作为 `untrusted_data` 卡片保存；测试证明其中即使包含提示注入文本，也不会直接返回个人事实或任务动作，陈旧资料会返回不可验证结果。[W2][T2]

这只能证明“搜索命中不会沿这条接口直接成为个人事实”。它没有把卡声明为现行“通用权威知识”一级类型、按六域/睡眠主题索引、记录具体准入用途或关联某项画像理解的支持/反对关系。

### 场景 E：提醒已经送达

现行合同只允许任务过程证据证明“提醒发生了什么”；送达不能证明主人行动或健康改善。[P1][P2] 候选任务能引用个人证据且不复制消息正文，是正确的最小化方向；但旧状态仍是 `candidate / scheduled / due_for_render` 等派发状态，过程事实没有成为独立任务过程证据卡，也没有与个人事实之间的类型门禁。[W3][T3] 四标签和验收另由后继任务能力票继续核验，本票只确认三类证据中的第三类尚不存在。

### 场景 F：AI 想新增“天气敏感性”二级主题

现行产品要求先向主人说明用途并取得同意。候选协议完整动作清单中没有主题提案、批准、拒绝或拓扑修订接口；任意 `dedupe_key` 不是主人批准证据。[W4] 因此这个门禁当前不可核验。

## 8. 交给完整 CAN 与后续 HOW 的事实边界

后续路线选择至少要能对以下行为给出可复现证据；这是一组验收边界，不是 schema 或技术方案：

1. 初始化后无需填满内容，但六域和每个固定二级主题都能被定位，空白明确显示未知。
2. 主题拓扑发生新增、改名、合并或删除时，先定位主人同意，再出现可追溯的拓扑修订；没有批准时状态不变。
3. 同一材料不能靠改标签在个人、通用或任务过程三类之间自动转换；每次准入只证明真实来源允许的范围。
4. 冲突、纠正、撤回、过期或适用性无法确认后，受影响画像理解退出当前或保持未知，旧卡和关系不被覆盖。
5. 画像主题和任务引用同一权威卡；复制正文、悬空引用、两个当前卡或任务 `solved` 直接生成个人事实都应失败。
6. 状态变化需用前后快照和引用关系验证，而不是以模型最终文字作为成功证据。
