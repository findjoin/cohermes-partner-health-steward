# AI 编码架构治理

> 当实施 Ticket 需要选择架构，或审查者要求重开既有架构时使用本规则。它只管理风险处置与收敛；`CONTEXT.md`、ADR、Map、Spec 和 Ticket 继续分别拥有领域、架构决定、路线、验收与状态，不建立第二套生命周期或账本。

## 权威与目标

- 目标是降低总项目风险，同时考虑产品与安全伤害、实现和状态复杂度、运行恢复、迁移兼容与交付延期。
- Reviewer 提交证据；顶层 Agent 负责分类和建议，不以多数票改变架构。用户决定产品目标、不可逆取舍和残余风险接受。
- 每个 Ticket 最多指向一份必要的增量设计；风险、决定和完成证据返回同一 Ticket 或既有 backlog。

## 编码前冻结

先核对当前实现，再写可观察结果、当前 Ticket 必须控制的现实故障和非目标。优先复用已经工作的 Module、Interface、Seam 与 Adapter；现有绿色行为不是待重写范围。

只冻结难以逆转的内容：

- 状态权威与唯一写入者；
- Module 职责、Interface、Seam 和依赖方向；
- 必须同成同败的事务边界；
- 外部副作用的不可逆点以及成功、失败、无法确认语义；
- 核心不变量；
- 已证明存在且必须保留的兼容、迁移和回滚边界；
- 本 Ticket 必须控制的现实故障。

内部字段、hash、codec、局部 SQL、helper、private method、文件布局和测试组织保持可逆，由编码 Agent 选择并通过行为验证。测试证明合同，不新增隐藏架构要求。

## 编码前收敛门

任何生产实现修改开始前，同一个 pre-code checkpoint 必须同时包含：

1. characterization：当前绿色行为、可复现差额、本票必须控制的现实故障和明确非目标；
2. 一份唯一增量冻结设计，只记录上一节列出的难逆决定；
3. 一份由独立 verification Agent 持有的冻结验证合同，以最高可用 Interface 和等价类证明既有验收，记录既有绿灯、预期红灯和回归命令；
4. fresh-context Spec reviewer 与 Standards reviewer 对同一 commit/tree 的编码前预审结论。

测试门以验收 ID 和能够杀死独立现实错误的 mutation 为单位，不按句子标点展开 Case registry，不做字段或故障的笛卡尔积，也不以测试数量作为充分性证明。编码 Agent 不得修改冻结设计、验证合同或 verifier-owned 测试；认为门错误时返回冻结阶段，由测试权威修订并形成新的 checkpoint。

只有上述四项可定位、预审通过且关键取舍已经交给主人确认后，才进入一致性编码。下游 Ticket 可以先保存产品验收输入，但其详细设计和测试门只在 blocker 闭合、当前代码可 characterization 时冻结，避免提前设计因上游变化失效。

## Finding 处置

每项 finding 在修改代码前只取得一种处置：

| 类别 | 处置 |
|---|---|
| 实现错误 | 已被冻结门复现时只修正实现；未被覆盖时停止并交回 verification 权威，确认它是否属于既有验收后形成新 checkpoint，不由编码 Agent 直接扩门，也不因此重开架构。 |
| 局部边界缺口 | 已被冻结门复现时在既有 Seam 或 Adapter 内做最小修复；未覆盖时停止并交回 verification 形成新 checkpoint。 |
| 运行／恢复风险 | 已在冻结设计与门内时使用既定可观测性、runbook 或恢复控制；未覆盖时停止并交回冻结阶段，不在实施审查中直接增加控制。 |
| 残余／延期风险 | 交用户有界接受，或写入带重新评估触发条件的既有 backlog。 |
| 结构性风险 | 暂停受影响实现，提交有证据的架构变更请求。 |

纯理论可能、没有现实触发链或不影响当前发布的意见不成为要求，也不自动进入 backlog。

## 重开与复杂度门

要求重开架构的人承担举证责任，必须同时给出：现实触发条件；“触发 → 当前机制失效 → 实际伤害”的完整因果链；可定位证据；被破坏的冻结不变量；现有局部门禁、Seam 隔离、运行恢复和风险接受均不足的理由；以及计入实现、状态、迁移、恢复和延期后仍能降低总风险的替代路线。上位硬约束被证据命中时立即阻塞受影响实现，但不自动授权某个替代架构。

每项新增保护同时说明它消除的风险与新增的权威状态、持久状态、Interface、故障组合和运维负担。应用删除测试：删除后复杂度直接消失、核心风险也没有回到调用者的机制应删除。不得为了证明既有权威再建立第二份 durable truth。

## 实施审查与停止

冻结后进入一致性实施：复用 pre-code checkpoint 已记录的 characterization 与冻结测试门，只对已证明的差额进行最小修改。实施审查只核对可观察验收、必须控制的故障、冻结一致性、回归和证据真实性；新 finding 仍按上表分类。

当可观察验收与必要验证通过、阻塞风险已有处置、没有通过举证门的结构性 blocker，且残余风险已由用户决定时，停止架构讨论并结束当前 Ticket。非阻塞建议留给既有 backlog；实现审查不得因另一种也合理的技术偏好继续扩写当前合同。
